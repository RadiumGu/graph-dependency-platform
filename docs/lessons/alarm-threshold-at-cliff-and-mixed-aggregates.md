## 一、本次事件的根因（已用证据确立）

单一模型 `jp.anthropic.claude-sonnet-4-6`（ap-northeast-1）延迟劣化约 5 倍。
**同区域其他模型完全正常**，因此不是区域性事件：

| 模型 | 最大延迟 | 状态 |
|---|---|---|
| `jp.anthropic.claude-sonnet-4-6` | 9.7s → 50.9s（峰值） | **劣化** |
| `jp.amazon.nova-2-lite-v1:0` | 1251 – 1338 ms | 正常 |
| `amazon.titan-embed-text-v2:0` | 87 – 110 ms | 正常 |

同时段 `InvocationThrottles` 与 `InvocationServerErrors` **均为空**，
`Invocations` 稳定在 25–44 次/30 分钟——**没有限流、没有服务端错误、我们的调用量没变**。

劣化形态是**高位震荡而非单调爬升**：01:46 见顶 50.9s 后在 9–38s 之间大幅摆动。

### 传导链

Waggle orchestrator 每个请求做多次模型调用 → 单次调用延迟 ×N →
petsite 端到端耗时从常态 15s 升到 45–68s → 越过内部 ALB 的 `idle_timeout=60s`
→ 客户端拿到 504 或 `IncompleteRead`。

实测的请求内时间线（petsite 容器日志，同一小时内逐次）：

```
01:20:35 → 01:20:48   13.2s
01:25:35 → 01:26:04   28.9s
01:35:35 → 01:36:14   39.8s
01:40:35 → 01:41:43   68.5s   ← 客户端在 60s 已被 ALB 掐断
```

**注意最后一行**：petsite 在 68.5 秒**完成了**工作才释放槽位，
比客户端放弃晚 8.5 秒。

## 二、判据缺陷一：预警阈值设在失败边界上，它只能事后确认

`crons/waggle_synthetic_traffic.py` 已经有延迟预警判据，但**它永远不会触发**：

```python
ALB_IDLE_TIMEOUT = 60
MAX_ELAPSED_SECONDS = 60          # ← 同一个数
...
if elapsed > MAX_ELAPSED_SECONDS:  # 到不了这里
    raise Report('⚠️ Waggle 应答变慢 …')
```

`elapsed` 一旦超过 60 秒，ALB 已经先掐断，控制流走的是 `HTTPError` /
`IncompleteRead` 分支，这条判据是死代码。

原注释把这当成优点写的——「取 60s ……**同时正好是内部 ALB 的 idle_timeout**」。
那句话正是它失效的原因：**阈值和悬崖是同一个数，悬崖永远先赢。**

### 代价可以量化

本次事件中位数的爬升过程：

```
逐小时中位数：  …16  17  16  16  19  22  28  34  49.6
                                  ↑ 这里就该响        ↑ 第一条 504
```

若阈值设在 `0.6 × ALB_IDLE_TIMEOUT = 36s`，**01:25 就会响**（28.9s 那轮之后），
而第一条 504 出现在 01:41。**约 3 小时的爬升期本来是可见的**，
但判据只看 504 这个二值，把正在爬升的连续量丢掉了。

### 通则

> **预警阈值必须在失败边界之下。设在边界上的阈值不是预警，是墓碑。**
>
> 推论：任何以「阈值正好等于系统上限」为理由的取值都是可疑的——
> 那个巧合说明作者在为「什么时候算失败」定义，而不是在为「什么时候该看一眼」定义。

### 实证：孤立长尾与持续故障，告警文案逐字节相同

2026-09-30 08:31 又收到一条 504（`adoption`）。查下来：

- 同一小时的成功轮次是 **15.1s**，完全正常；
- 此前**连续 26 小时零失败**；
- 两日合计 104 轮失败 10 次（10%），但其中 **9 次集中在那 5 小时窗口内**，
  今天这条是唯一的孤立事件。

**而这条孤立事件的告警文案，与 5 小时全面劣化期间的那 9 条逐字节相同。**
读者无法从告警本身分辨「系统正在挂」与「100 次里有 1 次慢」——
于是它拉动了一次完整的重新调查，结论是「没事」。

这正是第二节那个缺陷的另一面：判据只看单次是否越过悬崖，
既不看**趋势**（连续量），也不看**近期基线**（这次是否偏离常态）。
冷却窗口不能解决它——冷却只压重复，压不掉「一条孤立告警读起来像全面故障」。

**修法**：告警文案必须自带上下文，至少包含近期同类轮次的中位数与失败率。
一条写着「本轮 504；近 2 小时中位 15.1s、失败 1/24」的告警，
和一条写着「本轮 504；近 2 小时中位 49.6s、失败 9/12」的告警，
读者一眼就能分开——而现在这两种情况产出的是同一句话。

### 附带发现：注释里的基线会过时而无人察觉

原注释写「371 轮实测 p50=21.2s、max=32.6s，无一超 40s」。
事件当天中位数是 49.6s。**基线写在注释里就不会被重新验证**，
而一个基于过时基线的阈值读起来仍然很有道理。

## 三、判据缺陷二：聚合混合了不同总体，于是两边的真相都读不出来

不带维度查 `AWS/Bedrock` `InvocationLatency` 时看到：


我据此判断为「单一模型的双峰分布」——**结论是错的**。

## 四、我自己在本次调查中犯的同类错误（一并记录）

这些不是题外话：它们说明这个形状**对调查者同样有效**，

| 错误 | 为什么会错 | 纠正方式 |
|---|---|---|
| 判为「延迟长尾，无故障」 | 看的是 9 天**聚合** max，它把「窄分布 + 离群点」与「肥尾」混成一个数 | 按天拆开，发现当天分布只有 7.9–10.2s |
| 判为「AgentCore 返回空响应」 | `Received response: []` 与 `Released slot` 看起来像故障标记 | 做对照：`Released slot` 每小时正好 12 次 = 每个请求都有，**成功也有** |

| `grep 504` 统计历史 504 | 匹到了 `pid=2718504` 这类进程号 | 改用带结构的正则匹配 `END alarm=` 行 |
| 把探针降频到 30 分钟 | 与轮换周期共振，见下节——**且我是在写本文档的同时犯的** | 改为 25 分钟并用运行日志核实轮换恢复 |

### 降频与轮换周期共振：一次把「降噪」变成「偏测」的改动

探针按墙上时钟轮换提问：

```python
kind, question = QUESTIONS[int(time.time() // 300) % len(QUESTIONS)]
```

`QUESTIONS` 有 **6** 条，步长单位是 **300 秒**。
我把调度从 5 分钟改成 **30 分钟 = 6 × 300 秒** → 索引每次前进 6 →
**取模后恒为同一条**。实测证实（降频后连续 4 轮全是 `nutrition`，
而降频前同样 30 分钟内是 adoption/nutrition/adoption/ordering/adoption/adoption）。

两个损害，第二个更严重：

1. **轮换失效**：只压一条委派路径，而注释明确写了轮换是为避开语义缓存
   并覆盖不同工具。
2. **测量被偏置**：恒定选中的 `nutrition` 恰好是基线最高（约 25s）、
   最先越过 60s 悬崖的那条。于是失败率从「约 1/3」变成「4/4」——
   **告警系统性高报严重度**。同期降频前的 6 轮全部成功（27–56s）。

> **改采样周期时必须检查它与被采样系统内部周期的公约数。**
> 「降低频率」在直觉上只影响分辨率，实际可能同时改变**被采样的总体**——
> 那不是降噪，是换了个测量对象。

修法：周期取 **不是** `len(QUESTIONS) × 300` 的整数倍（已改为 25 分钟 = 5 × 300，
`gcd(5,6)=1` 故遍历全部 6 条）。**更根本的修法是让轮换不依赖墙上时钟**——
改用持久化计数器，否则任何满足共振条件的调度都会重新触发这个缺陷。

## 四之二、真实的时间去哪了：编排开销占 96%，真实工作占 4%

**2026-10-02 补记。** 前面各节都在量「端到端多久」，没有量「时间花在哪」。
拉 orchestrator runtime 的 OTel span 后，结构和此前所有推断都不一样。

数据源：`/aws/bedrock-agentcore/runtimes/WaggleAIOrchestrator-K85tG867Xt-DEFAULT`
（这是整条调查里最后才想到去查的地方，也是唯一给出分解的地方）

### 架构实况：两层 + 两轮

orchestrator 之下还有四个独立 AgentCore runtime
（`WaggleAIAdoption` / `WaggleAINutrition` / `WaggleAIOrdering` / `WaggleAIConcierge`），
经 `waggleaigateway-*.gateway.bedrock-agentcore` 调用。
每个请求走 **两轮** Strands event loop：

1. **第 1 轮**：LLM 决定调哪个工具 → 调用专家 runtime
2. **第 2 轮**：再调一次 LLM，把专家答案「重写得更友好」

### 两次失败的分解（不同路径，独立观测）

| 阶段 | `ordering` 21:21 | `adoption` 21:46 |
|---|---|---|
| 第 1 轮 路由 `chat` | 27.42s | 8.84s |
| 第 1 轮 `execute_tool`（**专家真实工作**） | **3.85s** | **31.95s** |
| **第 2 轮 `chat`（重新包装）** | **68.33s** | **>147s 未完成** |
| `POST /invocations` 总计 | **99.68s** | **>190s** |

`ordering` 那次：专家干活 3.85 秒，两次 orchestrator 自己的 LLM 调用合计
**95.74 秒 = 96%**。

### 结论：第 2 轮是主导项，且不产生信息

系统提示词原文要求 orchestrator
「return the specialist's answer to the user... Keep the final reply friendly and concise」。
而专家返回的**已经是用户可读的 markdown**——带标题、商品编号与价格、
`![图片](url)`、注意事项。为了「更友好」再付一次 LLM 往返，
代价是 69%（ordering）与 ≥77%（adoption）的预算。

> **优先级：去掉第 2 轮重新包装。** 它在两条不同路径上都是最大项与方差最大项。

**路由换轻模型降为次要**：两次观测分别是 27.42s 与 8.84s——
我曾据单样本断言「省 27%」，第二次观测就把它否了。
**又一次从一个样本推出比例**（见第四节同类错误表）。

**专家本身不该动**：3.85s 与 31.95s 是真实工作量差异。

### 附带确认：客户端被掐断后，服务端还在跑

两次都是 ALB 在 60 秒掐断客户端，而 orchestrator 继续工作——
第一次多跑 41 秒，第二次多跑 **≥130 秒**。
第五节那条「服务端工作边界由调用方耐心决定」的缺陷，
量级比 09-29 记录时严重三倍以上，且并发为 1 的探针**结构上看不到**由此产生的槽位饱和。

## 二之二、死阈值的实证：59.2 秒的应答被记为 `ok`

**2026-10-02 补记。** 第二节预测了「阈值设在悬崖上 = 不预警」的代价，
当晚拿到了实物：

```
20:55  adoption   21.5s  ok
21:21  ordering   504
21:46  adoption   504
22:11  nutrition  58.3s  ok     ← 距悬崖 1.7 秒，无告警
22:36  adoption   59.2s  ok     ← 距悬崖 0.8 秒，无告警
23:01  adoption   504
```

**一个 59.2 秒的聊天应答被判为成功。** 对聊天界面那是失败。

两种算法对同一段时间给出完全不同的结论：

| 判据 | 结果 |
|---|---|
| 探针的二值 ok/fail | 3/8 失败（37%） |
| 「可用」（<30s 可接受） | **21:21 之后 5 轮全部不可用（100%）** |

`MAX_ELAPSED_SECONDS = 60` 让 58.3s 与 59.2s 两轮静默通过。
若按本文建议设在 `0.6 × 60 = 36s`，两轮都会告警，
且会在 504 出现前就报。

1. **petsite 读 AgentCore 响应流没有超时。** 它的工作边界由调用方的耐心决定——
   实测跑到 68.5s 才收手，比 ALB 掐断晚 8.5 秒。
2. **Bedrock 连接槽位的 `WaitAsync` 无超时。** 槽位池有限，
   一个慢请求占用 50–70 秒；持续劣化下会饱和，健康请求被无界排队堵住。
3. **合成流量并发为 1，永远观测不到上面这个级联。** 真实用户会先撞上。
