# DP&R 三个优先项的可落地实施说明（P0×2 + P1×1）

> 生成时间：2026-09-08 · 视角：SRE + 图数据 + GenAI + AWS 合规
> 范围：从《技术深度分析》的七项路线图收敛为**三个最该先做的项**，每项给出「监管/标准条款 + 引用来源 + 数据模板 + 落地要求 + 验收标准」，直接可执行。
> 三项：**① P0 合规导出层（DORA RoI + BCBS 六列映射）② P0 Agent 层证伪 ③ P1 impact tolerance 阈值建模**。
> 术语：BCBS = Basel Committee on Banking Supervision（巴塞尔银行监管委员会，隶属 BIS）；POR = Principles for Operational Resilience（2021）；RoI = Register of Information（DORA 信息登记册）；IBS = Important Business Service（重要业务服务）。

## 项目一（P0）：合规导出层 —— DORA 信息登记册 + BCBS 六列映射视图

### 1.1 要满足的具体条款（引用来源）

| 法规 | 条款 | 原文要求 | 来源 |
|---|---|---|---|
| DORA | **Art. 28(3)** | 金融实体须在实体级/次合并级/合并级维护并更新一份「所有 ICT 第三方服务合同」的信息登记册（Register of Information） | [DLA Piper — The Register of Information](https://www.dlapiper.com/en-ma/insights/publications/law-in-tech/the-register-of-information-in-relation-to-contractual-arrangements-for-ict-services) |
| DORA | **ITS on RoI**（JC 2023 85，2024-01-17 终版） | 规定登记册的标准模板 RT.01–RT.99，每张表有字母数字标识 `RT.xy.wz`；合同终止后信息须保留满 5 年才可删除 | [ESAs Final Report on ITS on Register of Information](https://www.eba.europa.eu/sites/default/files/2024-01/30b47816-8d6d-432f-8dbd-b900c4306cf4/JC%202023%2085%20-%20Final%20report%20on%20draft%20ITS%20on%20Register%20of%20Information%20(1).pdf) |
| DORA | **EBA Data Model for DORA RoI**（2025-04） | 每个字段有编号与类型（如 `0060 - Name of the ICT third-party service provider in Latin alphabet, varchar(255)`）——**这是机器可读的字段级 schema**，图谱导出必须逐字段对齐 | [EBA Data Model for DORA RoI (PDF)](http://www.eba.europa.eu/sites/default/files/2025-04/035dd2b6-c7e3-4c7d-954f-6ffd41903de2/Data%20Model%20for%20DORA%20RoI.pdf) |
| BCBS | **POR Principle 4** | Mapping interconnections and interdependencies：银行须映射交付关键运营所必需的内外部互联互赖 | [BIS — Basel Consolidated Guidelines ORR/20](https://www.bis.org/committees/bcbs/basel-consolidated-guidelines/module/orr/20) |

### 1.2 DORA RoI 模板结构（导出层必须产出的表）

登记册按 `RT.xy.wz` 组织，导出层需从图谱生成以下表（重点是与依赖图强相关的 RT.05 / RT.06 / RT.07）：

| 表号 | 名称 | 图谱数据来源（我们怎么填） |
|---|---|---|
| RT.01 | 金融实体与集团 | 外部录入（组织信息，非图谱产出） |
| RT.02 | ICT 合同 | 合同系统；图谱补充"该合同支撑哪些 function" |
| RT.03 | 合同各方 | 合同系统 + `Vendor` 节点（见《技术深度分析》R2.3） |
| RT.04 | 使用 ICT 服务的实体 | 图谱：`BusinessService -[DependsOn]-> Vendor/SaaS` |
| **RT.05** | **ICT 服务供应链** | **图谱核心贡献**：RT.05.01 列全部供应商（含直接/集团内/分包商）；RT.05.02「每个供应商之间及其与子供应链的连接」= **依赖图的边**，变长路径遍历直接产出 |
| **RT.06** | **实体的功能** | 图谱：`BusinessService` 节点 + 其支撑链（`BusinessService → ... → Vendor`） |
| RT.07 | 服务评估 | 图谱补充「可替代性」——SPOF 查询判定该供应商是否单点 |
| RT.99 | 定义与术语 | 静态 |

> **关键落地点**：RT.05.02（供应链连接）和 RT.06（功能→支撑）本质就是依赖图的边遍历——这是本平台相较"填表工具"的差异化：**别人手工填 RT.05.02，我们从图谱自动生成，且每条边带 `verify_status`。**

### 1.3 BCBS 六列映射视图（SYSC 15A 对齐）

BCBS POR Principle 4 与英国 SYSC 15A 都要求把 IBS 映射到六类支撑要素。导出层产出一张表：

| 列 | 含义 | 图谱节点类型 | 当前覆盖 |
|---|---|---|---|
| People | 人员 | `Person` | 🔴 待建（R1.3） |
| Processes | 流程 | `Process` | 🔴 待建 |
| Technology | 技术 | Service/Pod/EC2/Lambda/DB | ✅ 已有 |
| Facilities | 场所 | `AvailabilityZone` | ✅ 已有（AZ 层） |
| Information | 数据/信息 | 数据基础设施（`AccessesData`）已有；数据资产血缘（Table/Column）🟡 部分 | 🟡 部分 |
| Third parties | 第三方 | `Vendor`/`SaaS` | 🔴 待建（R2.3） |

### 1.4 落地要求与工程步骤

1. **新增导出模块** `compliance_export/`（进程内 SDK，读 Neptune，openCypher）：
   - `export_dora_roi()` → 产出 RT.04/05/06/07 的 CSV，字段名严格对齐 EBA Data Model 编号（`0060` 等）。
   - `export_bcbs_mapping()` → 产出六列映射表，每 IBS 一行、每支撑要素一列，单元格列出支撑节点 + `verify_status`。
2. **每条导出的依赖边附带 `verify_status`**——这是审计增值项（见项目二/差异化）。
3. **保留期**：合同信息按 DORA 要求保留 5 年——图谱侧对应 `Vendor`/合同边不做硬删，只软删（`active=false`），与现有 TTL 机制一致（声明边 `expires_seconds=null`）。

### 1.5 验收标准

- [ ] 能对任一 IBS 一键导出 BCBS 六列映射表；技术/场所两列由图谱自动填充。
- [ ] 能导出 RT.05.02 供应链连接表，字段名通过 EBA Data Model 校验。
- [ ] 导出的每条关键依赖边带 `verify_status`（confirmed/inconclusive/untested）。
- [ ] **诚实标注**：静态声明边与 dynamic 观测边在导出表中分列统计，不混算"覆盖率"。

## 项目二（P0）：Agent 层证伪 —— 补上 GenAI 依赖的验证闭环

### 2.1 问题定义（为什么这是真 gap）

现状：Agent 层依赖（`Delegates`/`InvokesTool`/`Retrieves`，共 11 条 inference 边）里**主动探测只判定了 1 条边**。根因（已定位到 ENI 级）：DeepFlow 的 eBPF 采集器是 EKS 节点上的 DaemonSet，而 AgentCore 托管运行时不是 Pod、有独立的 `agentic_ai` 类型 ENI，实测对 6 个该类 ENI **零 L7/L4 记录**——**agent 边天生凑不出第二个被动观测源**。

### 2.2 依据的标准与来源

| 标准 | 内容 | 来源 |
|---|---|---|
| OTel GenAI 语义约定 | `gen_ai.*` 命名空间标准化 LLM/agent 遥测：模型调用、工具执行、agent 运行、检索、记忆操作的 span/属性/指标 | [OpenTelemetry GenAI Semantic Conventions Guide](https://hidekazu-konishi.com/entry/opentelemetry_genai_semantic_conventions_guide.html) |
| OTel GenAI 官方博客 | 标准化记录被调模型、输入/输出 token 数、（可选）prompt/completion/tool 调用完整内容 | [Inside the LLM Call: GenAI Observability with OpenTelemetry](https://opentelemetry.io/blog/2026/genai-observability/) |
| 评估层实践 | 对 **10–20% 生产流量**跑 LLM-as-judge 评分，平衡质量覆盖与评估成本；把 GenAI 语义约定当**版本化契约**管理 | [MLflow — LLM observability pipelines](https://mlflow.org/articles/tags/monitoring-llm-performance/) |

### 2.3 落地要求（三处必须换）

微服务证伪那套（在下游注入网络故障、看上游 success_rate/latency）**不能直接套用**到 agent，三处要换：

| 维度 | 微服务证伪 | Agent 证伪（要换成） |
|---|---|---|
| **判定指标** | success_rate / latency / error_count | **output_quality**（LLM-as-judge 评分 / 语义相似度 / 工具调用成功率 / 幻觉率）——agent 的"故障"表现为输出退化而非 HTTP 500 |
| **注入手段** | Chaos Mesh 打 Pod / FIS 打托管资源 | **agent 层注入**：① 改 MCP 工具白名单禁用某 Tool ② mock 某 Model 返回低质量结果 ③ 下线某 Sub-Agent；观测父 Agent 输出质量变化 |
| **观测源** | DeepFlow eBPF（打不通 AgentCore ENI） | **AgentCore Observability 的 OTel span**（`gen_ai.*`）作为第二观测源，`agentcore-etl` 已起头，需扩大覆盖 |

### 2.4 证伪实验模板（Agent 版，套用现有六阶段）

```yaml
experiment: agent-falsify-<edge_id>
edge: WaggleAIOrchestrator -[Delegates]-> WaggleAIAdoption   # 待验证的 inference 边
phase0_preflight:
  scope_check: 排除 platform/scaffolding（不打记录实验的管道）
  injectability: agent-layer（非 FIS/ChaosMesh 网络注入）
phase1_steady_state_before:
  observer: WaggleAIOrchestrator 的输出质量基线
  metric: llm_judge_score(3 采样 × N 次对话)   # 0-1 语义质量分
phase2_inject:
  method: disable_tool | mock_model_lowquality | offline_subagent
  target: WaggleAIAdoption
phase3_observe:
  metric: llm_judge_score 注入期
  stop_condition: 质量分骤降 > 阈值 或 错误率突增（区分 UserError/SystemError）
phase4_recover: 恢复 Tool/Model/Sub-Agent
phase5_steady_state_after: 确认质量分回到基线
verdict:
  confirmed: 注入后父 Agent 输出质量显著退化（依赖为真）
  refuted: 父 Agent 输出无变化（依赖存疑）
  inconclusive: 质量分方差过大 / 无法注入
```

### 2.5 观测盲区清单（GenAI 系统特有，已踩过并记录，直接写进 runbook）

- **失败调用不落节点**：X-Ray 服务图对失败的 agent 调用不产生下游节点——一次成功调用才建边。
- **session id ≥ 33 字符**：AgentCore `runtimeSessionId` 少于 33 字符返回 400，但兜底文案呈现为"连接中断"、HTTP 仍 200——极易误判为网络故障。
- **Errors 混 user/system**：`UserErrors`（坏请求）与 `SystemErrors`（runtime 坏了）语义相反，合并当健康信号会把 RCA 带偏（实测"26% 错误率"实为一小时突发平铺到 24h 的假象，稳态 0%）。

### 2.6 验收标准

- [ ] AgentCore OTel span（`gen_ai.*`）已作为独立观测源接入 `agentcore-etl`，覆盖全部 6 个 runtime。
- [ ] 至少对 5 条 inference 边完成 agent 层证伪（output_quality 判定），verify_status 写回图谱。
- [ ] LLM-as-judge 评分管道跑通，覆盖 10–20% 对话流量。
- [ ] 三条观测盲区写进运维 runbook。

## 项目三（P1）：impact tolerance 阈值建模（R1.4）

### 3.1 概念澄清（这是最容易做错的地方）

**impact tolerance ≠ RTO。** 必须先钉死区别，否则建模建错：

| 概念 | 定义 | 视角 |
|---|---|---|
| **RTO** | 恢复某个具体业务流程/服务的目标时间 | 内部、面向单个流程 |
| **impact tolerance** | 对某个**重要业务服务(IBS)**的**最大可容忍中断**——超过此点即对客户/市场/金融稳定造成**不可容忍的伤害**；且**假设中断已经发生** | 外部、面向危害后果 |

来源：[BNY Mellon — Impact Tolerances](https://bnymellon.com/content/dam/bnymellon/documents/pdf/emea/impact-tolerances-a-perspective-on-wholesale-markets-for-institutional-clients.pdf)（"Whereas RTOs are specific to recovery of a specific business process, impact tolerances are a measure of the maximum tolerable level of disruption to an Important Business Service"）；[FCA Impact Tolerances](https://www.fdcapital.co.uk/fca-impact-tolerances-setting-testing-reviewing/)（示例：某支付服务 **RTO=4 小时，但 impact tolerance=24 小时**——目标 4 小时恢复，但可接受最长 24 小时中断而不造成不可容忍伤害）。

### 3.2 依据的条款与来源

| 法规 | 要求 | 来源 |
|---|---|---|
| 英国 PRA/FCA SYSC 15A | 识别 IBS、**设定 impact tolerance**、映射所需资源、用**严重但可信场景(severe but plausible scenario)**测试能否守住容忍度 | [Bank of England — Impact tolerances for important business services (PDF)](https://www.bankofengland.co.uk/-/media/boe/files/prudential-regulation/publication/2021/building-operational-resilience-impact-tolerances-for-important-business-services.pdf) |
| BCBS POR | 银行须假设中断会发生，据"严重但可信场景"定义整体风险偏好与"tolerance for disruption" | [BIS — POR Executive Summary](https://bis.org/fsi/fsisummaries/op_resilience.pdf) |
| 方法论 | impact tolerance = IBS 发生不可容忍伤害前的最大可容忍中断，从客户/市场/金融稳定视角度量 | [Risk Publishing — Impact Tolerance Setting](https://riskpublishing.com/impact-tolerance-setting-a-practitioner-method/) |

### 3.3 图谱建模方案（在现有能力上加属性 + 一条查询）

现状：容灾计划生成器**已经算关键路径 RTO**，缺的只是「阈值 + 越界告警」。做法：

**Step 1 — 在 `BusinessService` 节点加属性**（走 C3 契约门禁，`NODE_ATTR_AUTHORITY` 约束谁能写）：
```yaml
BusinessService:
  impact_tolerance_seconds: 86400   # 最大可容忍中断（如支付=24h）
  rto_target_seconds: 14400         # 恢复目标（如 4h）——注意两者不同
  harm_dimension: [consumer, market, financial_stability]  # 伤害视角
  severe_plausible_scenario: "primary-AZ-outage"           # 测试场景锚
```

**Step 2 — 一条 openCypher 查询：找出「支撑链最坏恢复时间 > impact_tolerance」的 IBS**
```cypher
MATCH (ibs:BusinessService)
MATCH path = (ibs)-[:DependsOn|Calls|AccessesData*1..6]->(dep)
WITH ibs, max(reduce(t=0, r IN relationships(path) | t + coalesce(r.recovery_seconds,0))) AS worst_recovery
WHERE worst_recovery > ibs.impact_tolerance_seconds
RETURN ibs.name, worst_recovery, ibs.impact_tolerance_seconds,
       worst_recovery - ibs.impact_tolerance_seconds AS breach_gap
ORDER BY breach_gap DESC
```

**Step 3 — 与混沌证伪联动**：对 impact tolerance 越界的关键依赖边，优先安排故障注入验证（把"理论超界"升级为"实测超界"），`verify_status` 作为 SYSC 15A"用严重但可信场景测试"的证据。

### 3.4 落地要求

1. impact_tolerance 属性由**业务方设定**（风控/合规），不是技术推导——平台只提供承载与越界检测。
2. RTO 与 impact tolerance **必须分列**，不可混用（这是监管审查重点）。
3. 越界告警接入现有告警管道（如 EventBridge），按 IBS 分级。

### 3.5 验收标准

- [ ] `BusinessService` 节点支持 impact_tolerance / rto_target 双属性，且契约门禁约束写入权限。
- [ ] 越界查询能列出所有"支撑链最坏恢复 > 容忍度"的 IBS 及超界差值。
- [ ] 对越界 IBS 的关键边能触发混沌证伪，verify_status 回写作为合规测试证据。
- [ ] 报告中 RTO 与 impact tolerance 分列展示，不混算。

## 三项优先级与依赖关系

| 项目 | 优先级 | 前置依赖 | 工程量 | 最快见效点 |
|---|---|---|---|---|
| 一 · 合规导出层 | P0 | 无（技术/场所两列即可先出）；完整六列需 R1.3/R2.3 节点 | 低（导出层）+ 中（补节点） | 先出"技术+场所+verify_status"版，即可对监管演示 |
| 二 · Agent 层证伪 | P0 | AgentCore OTel span 接入（已起头） | 中 | 差异化 × GenAI 趋势交点 |
| 三 · impact tolerance | P1 | `BusinessService` 节点（与合规导出层共用） | 低 | 容灾生成器已算 RTO，接阈值即可 |

**共用底座**：项目一和项目三都依赖 `BusinessService` 节点建模——**先建这个节点类型，两个项目一起受益**。项目二独立、可并行。

**贯穿三项的差异化**：无论导出登记册、验证 agent 依赖、还是检测容忍度越界，都带 `verify_status`——"这条依赖/映射经过故障注入验证"是竞品给不出的审计级证据，也是回应 BCBS"映射能力普遍不达标"的直接抓手。
