## 三、⚠️ 网络架构：两个约束互锁成唯一解

### 推翻了 `01` 的一处 NOT FOUND（第 5 次「查不到 ≠ 不存在」）

`01` 写「VPC Lattice 能让 Gateway 直连 ClusterIP —— NOT FOUND」。
实查 `create-agent-runtime` 的参数后：

```
--network-configuration  networkMode=PUBLIC|VPC
                         networkModeConfig={securityGroups=[...],subnets=[...],
                                            requireServiceS3Endpoint=bool}
```

**AgentCore Runtime 原生支持 `networkMode: VPC`**，Gateway 另支持
`managedVpcResource` / 自管 `LatticeResource`。

### 互锁关系

1. 安全硬约束「ALB 上不得新增公网入口」 → agent 只能走 **internal ALB**
2. internal ALB 是 `scheme=internal`，**只在 VPC 内可达** → Runtime **必须** `networkMode: VPC`

**把 Runtime 设成 PUBLIC 模式，它根本连不上 internal ALB，而唯一的"修复"就是开公网入口
—— 那正是被禁止的。** 所以架构是被约束逼出来的唯一解，不是选择。

### 但 `.svc.cluster.local` 仍然不通

即使 VPC 模式下也不通：集群内 DNS 由 **CoreDNS** 提供，而 VPC 里的 ENI 用的是
**Route53 Resolver**。（ClusterIP 本身也是 kube-proxy 的节点内虚拟 IP，非 VPC 可路由。）

**实测确认六个服务全是 ClusterIP**：
```

pay-for-adoption    ClusterIP  80
pethistory-service  ClusterIP  8080
search-service      ClusterIP  80
service-petsite     ClusterIP  80
traffic-generator   ClusterIP  80
```

| agent 需要 | 现状 |

| `petfoodcarturl` | ❌ 不存在 |

**三个"存在"的值全部指向 ClusterIP DNS，AgentCore 用不了。**

### 处置：另建 `/petstore/agent/*`，现有参数保持不动

现有参数服务于集群内的 petsite，改掉会波及正在运行的应用。
所以新建一组指向 internal ALB 的参数，并把 `PARAMETER_STORE_PREFIX` 设为 `/petstore/agent`。

internal ALB 当前只有两个 listener（实测）：

```
:8081 → petsite-lt-search-tg   健康=healthy,healthy    ← search-service，可直接用
:80   → petsite-lt-tg          健康=healthy,healthy    ← petsite
```

**需要新增 internal listener**（不动公网 ALB）：`list-adoptions`、`pay-for-adoption`，
以及将来的 `petfood`。

> ⚠️ **新增 listener 应走 CDK 而不是手工 `aws elbv2`**：该 ALB 的 listener 子树已有
> 6 个悬空的 CFN 物理 ID（在 CloudFormation 之外被重建过），手工新增会加深这笔债。

## 五、⚠️ 一个默认值会让 Stage 2 的 `Delegates` 边永远为空

`orchestrator_strands/delegate.py`：

```python
TRANSPORT = os.getenv("AGENT_TRANSPORT", "local")
_TARGETS = {"nutrition": os.getenv("NUTRITION_TARGET", "nutrition"), ...}
# gateway 模式：url = f"{gateway}/{_TARGETS[agent]}/invocations"，httpx.post + SigV4
```

| 传输模式 | 部署形态 | 对图谱的后果 |
|---|---|---|
| `local`（**上游默认**） | 五个 agent 在**同一容器**，委派是进程内函数调用（lazy import） | 图里只有 **1 个 `AgentRuntime` 节点、0 条 `Delegates` 边** |
| `gateway` | 5 个独立 Runtime + Gateway，委派是带 SigV4 的跨 Runtime HTTP | 委派在 `aws/spans` 里可见，`etl_agentcore` 才建得出 `Delegates` 边 |

Stage 2 刚把 `Delegates` 加进契约并放进 `PENDING_FIRST_EDGE`，
而我在那里写明「永远为空就等于永远放弃对它的存在性检查」。

**这个项目的核心是依赖图谱，所以必须 `AGENT_TRANSPORT=gateway`。**
这也意味着部署形态是 **5 个 Runtime + 1 个 Gateway**，不是 1 个容器。
