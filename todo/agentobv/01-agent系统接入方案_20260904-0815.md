# PetSite 集群接入 Agent 系统：方案与取舍

**日期**：2026-09-04 08:15 UTC
**问题**：在已部署的 PetSite 集群里加一个 agent 系统，尽量用 AWS 托管的 AgentCore，与现有应用有机集成。
**核心结论**：**不要从零设计——上游 `aws-samples/one-observability-demo` 已经建好了，而且正是这个形态。真正的工作是移植，而移植成本来自 fork 已落后 277 个提交且上游重构了整个目录布局。**

### AgentCore Runtime 的入口契约 **[上游代码]**

`common/agentcore_server.py`：

```python
from bedrock_agentcore.runtime import BedrockAgentCoreApp

def build_app(run):                    # 同步
    app = BedrockAgentCoreApp()
    @app.entrypoint
    def handler(payload): ...

def build_streaming_app(stream):       # 流式
    app = BedrockAgentCoreApp()
    @app.entrypoint
    async def handler(payload): ...
```

即：**agent 只要实现一个 `run()`，用 `BedrockAgentCoreApp` 包一层就能跑在托管 Runtime 上**，不需要自己写 HTTP 服务。

## 三、三条可选路径与推荐

### 路径 A：只移植 agent 模块，不动布局（**推荐**）

把 `waggle_ai_agents/` 与 6 个 `waggle-ai-*.ts` 构造摘出来，适配到本地 `PetAdoptions/cdk/pet_stack` 的现有结构上。

- **优点**：本地 35 个提交零冲突；`ServicesEks2` / `Applications` 两个 stack 不动；agent 作为**第三个 stack** 独立部署，爆炸半径与现有五个微服务隔离。
- **缺点**：与上游永久分叉，上游后续 agent 更新要手工跟。
- **工作量估计**：agent 代码本身可几乎原样搬（它只依赖 `bedrock_agentcore` + 各框架，不依赖 PetSite 的 CDK 结构）；6 个 CDK 构造要改的是 props 来源与命名，不是逻辑。
- **前置**：本地需装 `strands-agents`、`bedrock-agentcore`（**[实测]** 当前 Python 环境这两个都未安装）。

### 路径 B：整体升级到上游布局

- **优点**：一次性拿到 agent + `petfood-rs` + 文档站，之后跟上游成本最低。
- **缺点**：277 个提交的跨布局合并；本地 35 个提交要逐个重做（其中 keep-alive 修复的目标文件在上游已不存在）；`ServicesEks2` 那个悬空 ALB listener 子树在新布局下行为未知。
- **判断**：**不建议在这个阶段做**——它把「加一个 agent」变成了「重做整套部署」，两件事的风险不该绑在一起。

### 路径 C：完全自建 agent，不参考上游

- **不建议**。上游那套已经解决了跨框架可观测性、AgentCore 入口契约、Guardrails、Memory、KB 的接线，自建等于重复劳动且拿不到官方样例的验证。

## 四、Agent 怎么调到 PetSite 的私有服务（原本的死结，已解开）

**[实测]** PetSite 五个微服务全是 `ClusterIP`，没有一个对外：

```
list-adoptions / pay-for-adoption / search-service / service-petsite   ClusterIP 80
pethistory-service                                                     ClusterIP 8080
```

托管的 AgentCore 跑在 AWS 侧，怎么打进 VPC 里的 ClusterIP？**官方有机制。**

### 出站：AgentCore Gateway 经 VPC Lattice 进 VPC **[官方文档]**

> "AgentCore Gateway supports connecting to self-hosted MCP servers running inside your VPC using private endpoints powered by **Amazon VPC Lattice**. You can configure a `privateEndpoint` on your gateway target to route traffic privately to your MCP server without exposing it to the public internet."
> — https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/gateway-vpc-egress.html

> "Amazon Bedrock AgentCore supports private connectivity to resources hosted inside your AWS VPC ... such as private MCP servers, **internal REST APIs**, or databases, without exposing those services to the public internet."
> — https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/vpc-egress-private-endpoints.html

两种模式：**Managed VPC resources**（只给 VPC/子网/SG，AgentCore 托管 Lattice 资源，不需要 Lattice 的 IAM/SCP）与 **Self-managed Lattice**（自建，可跨账号经 RAM）。

**硬边界（官方明确列举，必须照做）**：

| target 类型 | 是否支持 `privateEndpoint` 进 VPC |
|---|---|
| MCP server | ✅ 支持 |
| OpenAPI 规范 | ✅ 支持 |
| **Smithy 模型** | ❌ **不支持** |
| **API Gateway REST API** | ❌ **不能直接进 VPC**（需 API Gateway 侧用 VPC Link，或导出成 OpenAPI + `privateEndpoint`） |

### 入站：PrivateLink **[官方文档]**

> "When you host your application in an AWS VPC, you can establish private connectivity to the AgentCore Runtime and AgentCore Gateway APIs by adding the **AgentCore VPC endpoint** to your VPC. This enables secure API calls, without internet traversal, through VPC PrivateLink inbound connections."
> — https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/agentcore-vpc.html

### Gateway 支持的 target 输入（把已有 API 变 tool）**[官方文档]**

> "MCP targets operate in aggregation mode. The gateway combines the capabilities of all MCP targets into a single unified virtual MCP server. ... MCP target types include **Lambda functions, API Gateway REST APIs, OpenAPI specifications, Smithy models, MCP servers**, built-in integration provider templates and built-in connectors to tools."
> — https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/gateway-core-concepts.html

### ⚠️ 一处必须修正的细节：VPC Lattice ≠ 能直连 ClusterIP

**「Gateway target 直接对准裸 ClusterIP」在官方文档里是 NOT FOUND。** 官方说的是「私有 MCP server、内部 REST API、数据库」这类 VPC 内资源，**没有任何一处**说可以把 target 指向 Kubernetes 的 ClusterIP。

所以 VPC Lattice 解决的是「不走公网进 VPC」，**不是**「直连 ClusterIP」。PetSite 的五个 ClusterIP 服务前面**仍然需要一层东西**作为 Lattice 的目标：

- **选项 i**：一个 internal LB（可复用已有的 `petsite-internal-lt`，或新建专供 agent 的）
- **选项 ii**：在 VPC 内自建一个 MCP server（Pod 或 Lambda），由它去调 ClusterIP —— 这样 Gateway 的 target 就是「私有 MCP server」，完全落在官方明确支持的形态里

### 落到 PetSite 的具体接法（三个选项，已按修正后的事实重排）

**接法 1：VPC 内自建 MCP server 作适配层 + Gateway MCP target + `privateEndpoint`（推荐）**
- 在集群里跑一个小的 MCP server（arm64），它用 ClusterIP DNS 直接调五个微服务——集群内调用零网络改造。
- Gateway 的 target 类型是「私有 MCP server」，**这是官方明确支持 `privateEndpoint` 的形态**。
- 可复用 `awslabs/run-model-context-protocol-servers-with-aws-lambda`（含 `BedrockAgentCoreGatewayTargetHandler`），或直接写一个 MCP server 部署进集群。
- 优点：不新增任何对外入口；不动那个有悬空 CFN 引用的 ALB；tool 定义集中在一处便于观测。
- 代价：多一个自建组件（与「尽量用托管」有一点张力，但这是官方支持形态里唯一不动现有网络的）。

**接法 2：给微服务写 OpenAPI 规范 + OpenAPI target + `privateEndpoint`**
- 需要在 ClusterIP 前放 internal LB 作为 Lattice 目标。
- 可复用已有的 `petsite-internal-lt`（**[实测]** `:80` → petsite、`:8081` → search-service），其余三个服务要新加 listener + TargetGroupBinding。
- 缺点：要动那个 ALB——而它的 listener 子树在 CloudFormation 之外被重建过（6 个资源物理 ID 全悬空），动它有已知风险；而且把「压测入口」与「agent 入口」耦合在同一个 ALB 上，职责混了。

**接法 3：把 agent 直接放进 EKS 集群（不用托管 Runtime）**
- 集群内调 ClusterIP 零障碍，连通性问题直接消失。
- 但**与「尽量用托管 AgentCore」的要求相悖**，且 agent 观测要自己接 ADOT SDK（见 `02` 第三节）。
- 官方有样例：`awslabs/agentcore-samples` 的 `03-integrations/agents-hosted-outside-runtime/agents-on-eks`。
- 保留为备选：若东京区某个 AgentCore 组件实测不可用，这是退路。

**推荐接法 1**——它是「官方明确支持的 target 形态」与「不动现有网络资源」的唯一交集。

## 五、部署这套东西必须知道的既有债务

这些是本地环境的既有状态，**不处理会直接把部署卡住**：

1. **`ServicesEks2` 部署必须带 context 覆盖** **[实测]**
   ```bash
   cdk deploy ServicesEks2 \
     --context acm_certificate_arn=arn:aws:acm:ap-northeast-1:926093770964:certificate/a661c9dd-c539-48b8-bb7f-ea8d8e46da9d
   ```
   原因：ALB 的 :443/:80 两个 listener 加 4 条规则的 CFN 物理 ID 全部悬空（在 CloudFormation 之外被重建过），不带这个覆盖会让 listener 的 UPDATE 报 `NotFound` 并卡进 `UPDATE_ROLLBACK_FAILED`。
   **如果 agent 作为独立 stack 部署，就完全绕开了这个问题**——这是路径 A 的一个额外好处。

2. **`eks-service.ts` 是四个 EKS 服务共用的构造** **[实测]**
   已有 `cpuLimit` / `memoryLimit` / `startupGraceSeconds` / `probeTimeoutSeconds` 这套「可选 props」先例。若 agent 需要进集群（而非只跑托管 Runtime），照这个模式加参数，不要改共用默认值。

3. **节点容量** **[实测]** 4 × `t4g.xlarge`（`allocatable cpu=3920m`），当前水位 151–250m。容量不是约束。但注意**节点是 arm64**——如果 agent 要进集群，镜像必须 `platform: Platform.LINUX_ARM64`（本地 CDK 里 petsite 那个 asset 已因此补过 platform 钉住）。

4. **`petsite` 没有 otel sidecar** **[实测]** 另外四个服务有 `aws-otel-collector`，petsite 在 2026-08-29 撤回过。这与 agent 观测方案直接相关（见 `02`）。

## 六、给出的推荐

**路径 A + 接法 1 + 独立 stack**：

1. 从上游摘 `waggle_ai_agents/` 与 6 个 `waggle-ai-*.ts`，适配到 `PetAdoptions/cdk/pet_stack/lib/`。
2. 新建第三个 stack（如 `WaggleAgents`），不碰 `ServicesEks2` / `Applications`，绕开 ALB 悬空债务。
3. Agent 跑在 **AgentCore Runtime**（托管，符合"尽量用托管"的要求）。
4. Agent 调 PetSite 私有服务：**集群内自建一个 MCP server 作适配层**（arm64，用 ClusterIP DNS 直调五个微服务），Gateway 以「私有 MCP server」为 target 配 `privateEndpoint` 经 VPC Lattice 私有路由。**不新增任何对外入口，也不动那个有悬空引用的 ALB。**
5. 会话记忆用 **AgentCore Memory**，RAG 用 **Bedrock Knowledge Base**（上游 `waggle-ai-nutrition-kb.ts` 现成）。
6. 前端集成：上游是在 petsite 里做 "Waggle" 聊天界面。本地 petsite 已有 `PetFoodController.cs` **[实测]**，可作为切入点。
7. 工具调用治理可选加 **AgentCore Policy**（Cedar 策略，GA 2026-03，在 Gateway 每次工具调用前拦截）——对「禁用某个 tool 做故障注入」正好是现成开关。

**未验证、需在动手前实测的项**（不要当已知）：
- AgentCore **逐个工具组件**在 ap-northeast-1 的可用性。**[实测]** 只确认了控制面可达（`list-agent-runtimes` 返回空列表而非报错）与官方 GA 公告的九个区域含东京；**逐组件区域表未取到**（`agentcore-regions.html` 正文 NOT FOUND）。
- Bedrock 上 Claude Sonnet 4.6（上游 orchestrator 用的模型）在东京区是否已开通。
- **VPC Lattice 的 Managed VPC resources 模式在东京区是否可用**——这是接法 1 的关键依赖，不可用则退到接法 2 或 3。
- 上游那 6 个 CDK 构造对 props 的依赖面（是否引用了新布局下才存在的共享构造），决定移植工作量的真实大小。
