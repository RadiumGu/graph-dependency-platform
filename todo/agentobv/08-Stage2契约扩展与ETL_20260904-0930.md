## 一、计划里写错的两处（动手才发现）

### ① `Invokes` 边类型**早就存在**，不能拿来用

计划写「新增 3 边类型：Invokes / Delegates / Retrieves」。实际契约里 `Invokes` 已有：

```yaml
Invokes:
  src: [LambdaFunction, SNSTopic, StepFunction]
  dst: [LambdaFunction]
  dependency: false          # ← 关键
```

它是 **`dependency: false` 的结构边**，而 agent 对 tool 是**真依赖**（tool 拿不到结果
agent 就答不出）。把两种语义塞进一个标签，会让「按 dependency 过滤」的依赖查询
同时命中结构边与依赖边 —— 那正是本契约区分两者要避免的事。

**处置**：新建 `InvokesTool`（`dependency: true`, TTL 21600），不动原 `Invokes`。

### ② 要暂停的调度规则是 **4 条不是 2 条**

GOAL.md 写「disable 5min/15min 的 ETL 规则」。实测自动发现的结果：

```
🟢 neptune-etl-cfn-daily      cron(0 18 * * ? *)  → neptune-etl-from-cfn
🟢 neptune-etl-every-15min    rate(15 minutes)    → neptune-etl-from-aws
🟢 neptune-etl-every-5min     rate(5 minutes)     → neptune-etl-from-deepflow
🟢 neptune-etl-xray-hourly    rate(1 hour)        → neptune-etl-from-xray
```

**按计划硬编码 2 条会漏掉一半** —— 其中 `neptune-etl-xray-hourly` 恰恰是重建期间
最会写噪声边的那个（拓扑源）。所以脚本改成**按 Lambda 名前缀自动发现**。

## 二、契约改动

### 新增 6 节点类型

| 类型 | 身份键 | TTL |
|---|---|---|
| `AgentRuntime` | `arn` | 604800 |
| `AgentTool` | `tool_key`（复合键） | 604800 |
| `AgentGateway` | `arn` | 604800 |
| `AgentMemory` | `arn` | 604800 |
| `KnowledgeBase` | `arn` | 604800 |
| `Guardrail` | `arn` | 604800 |

**一次性红利**：这六类只由 `etl_agentcore` 一个 ETL 写，**没有 etl_cfn 并写的历史包袱**，
所以能直接用 `arn` 做身份键 —— 不必像 `LambdaFunction` / `DynamoDBTable` 那样被
`preferred_blocked_by` 卡着用 `name`（见 test_35::g13）。新类型只有这一次机会做对。

**`AgentTool` 为什么用复合键 `<owner_arn>#<tool_name>`**：tool 没有 ARN，它是 agent
进程内注册的函数或 Gateway 聚合出的虚拟 MCP 工具。**只用 `tool_name` 会把两个 agent
各自注册的同名 `get_pet` 并成一个节点** —— 与 FIS chaos 模板里「tool 名精确匹配、
名字对不上就零注入而实验仍报成功」是同一个坑。

身份键一律钉 **AWS 侧标识**，刻意**不用** `gen_ai.*`（semconv 里 stability 全是
`development`，没有一个 stable，而契约要求身份键不可变）。

### 新增 3 边类型（全部 `dependency: true`, TTL 21600）

| 边 | src → dst | 说明 |
|---|---|---|
| `Delegates` | AgentRuntime → AgentRuntime | 编排 agent 路由到子 agent |
| `InvokesTool` | AgentRuntime → AgentTool | 见上，刻意不复用 `Invokes` |
| `Retrieves` | AgentRuntime → KnowledgeBase | KB 检索 |

TTL 统一 21600（6h）与 `AccessesData` 一致 —— 同为 span 派生，用同一个源窗口。
取值不同会出现「一条边失效了、同源的另一条还在」的不一致。

### 扩展 4 个现有边（而非新造）

| 边 | 新增的 pair | 理由 |
|---|---|---|
| `AccessesData` | `AgentRuntime → AgentMemory`、`AgentRuntime → AWSServiceEndpoint` | 读写 Memory；调 Bedrock 模型与 `Microservice → AWSServiceEndpoint` 同构，故不新造 `InvokesModel` |
| `ProtectsAccess` | `Guardrail → AgentRuntime` | 与 `SecurityGroup → LambdaFunction` 同构：一道策略保护一个执行体 |
| `RoutesTo` | `AgentGateway → AgentTool` | 与 `LoadBalancer → TargetGroup` 同构：入口分发到后端单元 |
| **`DependsOn`** | **`AgentTool → LambdaFunction`、`AgentTool → Microservice`** | ★ **把 agent 子图接回既有 PetSite 图的唯一通路** |

**最后那条是本 Stage 最重要的设计决定。** 缺了它，六个 agent 节点类型会在图里形成
一座孤岛 —— 能查到 agent 内部结构，却回答不了「petsite 挂了会影响哪个 agent」，
而那恰恰是这个图谱存在的理由。

## 三、测试侧修了一处不对称、被测试挡回一次

### ① 边侧缺零实例允许名单（节点侧有）

`test_s0_01`（节点）**通过**了，因为我把 6 个新类型加进了 `PENDING_FIRST_INSTANCE`。
但 `test_s0_02`（边）**失败** —— 边侧**根本没有对应的允许名单**。

「已声明但尚未产生实例」对边和对节点是同一种合法中间态。只给节点开口子，
等于要求「新增边类型必须与写入它的 ETL 同一秒上线」，那做不到。

**处置**：加 `PENDING_FIRST_EDGE`，并在注释里写明 Stage 4 之后必须移除 ——
留在名单里等于放弃对这三条边的存在性检查，而它们是 agent 依赖图的**全部内容**，
静默为空是最坏情况。

### ② `test_42` 挡回了我加的 `identity_note` 字段

我给 `AgentTool` 加了 `identity_note` 解释复合键的理由。`test_m07` 失败：

> 这些元字段在契约里有声明但 graph_contract 没有读取函数: `['identity_note']`。
> 没有 accessor 的字段会变成过期而无人知晓的注释。

测试的理由是对的。两个选项：造一个 `identity_note_for()` accessor，或改用契约认可的
自由文本字段 `note`。**选了后者** —— 造一个没有任何调用方的 accessor 只是把同一个
「写了但没人读」的缺陷上移一层，那是满足测试字面而非其意图。

## 四、新 ETL：`infra/lambda/etl_agentcore/neptune_etl_agentcore.py`（511 行）

### 两条链路刻意分开

| 链路 | 产出 | 失败表现 |
|---|---|---|
| 控制面 API（`bedrock-agentcore-control` / `bedrock` / `bedrock-agent`） | 资源节点 + 静态边（`RoutesTo` / `ProtectsAccess` / `DependsOn`） | **节点缺失** |
| `aws/spans` 结构化日志（Logs Insights） | 调用边（`Delegates` / `InvokesTool` / `Retrieves` / `AccessesData`） | **边缺失**（「有 agent 但没有依赖」） |

**调用边只能来自 span**：控制面 API 看不到「谁调了谁」。Runtime 列表告诉你有哪些
agent，**不告诉你 orchestrator 路由到了哪个子 agent** —— 那只存在于运行时 span 里。
与 `etl_xray` 只能从 `GetServiceGraph` 拿拓扑是同一个道理。

### 「空」与「拿不到」必须区分（`_probe_status`）

`[]` 与「调用失败」在下游看起来一样，含义却相反：前者是「确实没有 agent」，
后者是「我不知道有没有」。**把后者当成前者，会让权限丢失表现为「图里 agent 消失了」
而无人报警** —— 与 X-Ray 双源验证踩过的坑同形（`verified_by` 属性就是为它加的）。

**本地实测验证通过**：

```
runtimes     status=empty   0 条      ← 确认为空，非失败
gateways     status=empty   0 条
memories     status=ok      1 条      ← xgg_memory-5M0VYBCeFS
guardrails   status=empty   0 条
kbs          status=empty   0 条
spans        status=empty   0 条      ← TS 已开但还没有 agent span，符合预期
失败项: []
```

### 其他设计要点

- **全程走契约门禁**（`assert_node_type` / `assert_edge_type` / `assert_source` / `identity_prop_for`）
- 顶点属性一律 `property(single, ...)` —— 默认 SET 基数会静默累积多值（本仓库为此清理过 1,897 个冗余值）
- `source` / `dependency_kind` / `first_seen` **只在新建时写**（契约的 `edge_write_once_attrs`）—— `etl_aws` 与 `etl_cfn` 都犯过无条件覆盖的错，见 g08
- `_backend_ref` **只解析 Lambda target**，OpenAPI / 外部 MCP server 的后端是 URL，映射到哪个 Microservice 需要对照表，**刻意不猜**（猜错会造出一条假依赖边，比缺一条边更糟）

## 五、顺带查出的一个真缺口（未修，需决策）

**`etl_xray` 与共享写入层 `neptune_client_base.py` 完全没有接契约门禁。**

```
etl_xray       引用 graph_contract 的文件数: 0     ← 无门禁写入
etl_trigger    引用 graph_contract 的文件数: 0
etl_aws        引用 graph_contract 的文件数: 4
etl_cfn        引用 graph_contract 的文件数: 3
etl_deepflow   引用 graph_contract 的文件数: 1
```

而契约文件开头明确写着「合法的 source 取值词表。**由 graph_contract.assert_source()
在写入时强制**」。**对 `etl_xray` 这条路径，这句话不成立。**

这与契约存在的初衷直接冲突（「在引入本文件之前，四个写入 ETL 无一 import profiles，
运行时对节点/边类型零校验」）—— 修了三个，漏了一个。

**未修的原因**：属于既有 ETL 的改造，不在 Stage 2 声明的范围内，且改动写入路径需要
单独验证（`etl_xray` 每小时跑，改错会污染拓扑源）。**已记录，建议在 Stage 6 图谱验收前处理。**

## 六、`scripts/etl_schedule_pause.py`（141 行）—— 写了但**刻意没执行**

**为什么没执行**：Stage 3 还没开始拆应用。现在暂停只会让图白白变陈旧 6 小时以上，
没有任何收益，而且增加「忘记恢复」的风险。**正确的触发点是 Stage 3 真正开始重建应用时。**

设计要点：
- **只改 `State`，绝不删除**（用户硬约束：ETL 可改不可删）
- **自动发现**而非硬编码（正因如此才发现是 4 条不是 2 条）
- 只收**有 `ScheduleExpression`** 的规则 —— 事件驱动的规则（`neptune-etl-trigger-eks` 等）
  **不该暂停**：它们由真实基础设施变更触发，那正是重建期间最需要记录的信号
- `--pause` 把原状态存盘，`--resume` **只还原暂停前是 ENABLED 的**（本来就 DISABLED 的
  规则若被打开，就是擅自改变了配置）
- **无存盘时 `--resume` 拒绝执行** —— 已实测：「无从判断哪些规则本来是开着的，
  擅自把所有规则打开会改变暂停前的配置，故拒绝」
