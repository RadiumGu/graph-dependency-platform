### ⚠️ 验证 3：模型——五个 agent 里四个能对等替代，**一个在东京完全没有**

上游 `common/models.py` 是模型的唯一真源，五个 agent 的默认值**三个硬编码了 `us.` 前缀**。`us.` 是美国跨区域推理 profile，**无法从东京调用**。

| Agent | 上游默认 | 东京对等 | 判定 |
|---|---|---|---|
| orchestrator | `us.anthropic.claude-sonnet-4-6` | **`jp.anthropic.claude-sonnet-4-6`** | ✅ 同版本，且 **jp 本地**（数据留日本境内） |
| nutrition | 同上 | 同上 | ✅ 同上 |
| ordering | `us.amazon.nova-2-lite-v1:0` | **`jp.amazon.nova-2-lite-v1:0`** | ✅ 同版本，jp 本地 |
| concierge | `GPT_OSS`（config） | **`openai.gpt-oss-120b-1:0`** | ✅ **ON_DEMAND 可直调**，连 profile 都不需要 |
| **adoption** | `us.meta.llama4-maverick-17b-instruct-v1:0` | **❌ 东京无任何 Llama** | ❌ **唯一真阻塞** |

东京 profile 前缀分布：`jp.` 6 个、`apac.` 8 个、`global.` 19 个。

**关于 adoption 的处置**：LlamaIndex 是**框架**，跑在 Bedrock Converse 上，并不要求模型必须是 Llama——只是上游恰好配了 Llama。东京可选的替代：`jp.anthropic.claude-sonnet-4-6`（保持与 orchestrator 一致）、`jp.anthropic.claude-haiku-4-5-20251001-v1:0`（更省）、`openai.gpt-oss-120b-1:0`、`mistral.mistral-large-3-675b-instruct`、`deepseek.v3.2`。

> **推荐 `jp.anthropic.claude-haiku-4-5`**：adoption 是检索+组装型任务，不需要顶配推理；同时保持 jp 本地。

**关键的好消息——这是配置活不是代码活**：`models.py` 里每一项都可用环境变量覆盖（`ORCHESTRATOR_MODEL_ID` / `NUTRITION_MODEL_ID` / `ORDERING_MODEL_ID` / `ADOPTION_MODEL_ID` / `CONCIERGE_MODEL_ID`，以及 `BEDROCK_CLAUDE_MODEL_ID` / `BEDROCK_NOVA_LITE_MODEL_ID` / `BEDROCK_LLAMA_MODEL_ID` / `BEDROCK_GPT_OSS_MODEL_ID`）。**模型改区只需在 CDK 里设 5 个环境变量，不动一行 agent 代码。**

### ✅ 验证 4：`concierge_openai` 不需要 OpenAI API key

`deploy/requirements.concierge.txt` 首行与 `agent.py` 写得很直白：

```
# Concierge runtime (OpenAI Agents SDK -> Bedrock via LiteLLM / SigV4).
openai-agents[litellm]

# agent.py:
# No OpenAI platform account here — disable the SDK's hosted tracing exporter.
model=LitellmModel(model=models.litellm_model("concierge"))
```

而 `models.litellm_model()` 返回 `f"bedrock/{model_id(agent)}"`。

**结论**：用的是 OpenAI SDK 作为**框架**，推理走 Bedrock + SigV4 标准凭证链。**没有外部付费依赖，与「尽量用 AWS 托管」不冲突。** `ordering_crewai` 同理走 `bedrock/` 前缀的 LiteLLM。

## 二、范围硬约束（用户 2026-09-04 明确）

| 对象 | 可否重建 |
|---|---|
| **Neptune 图数据库** | ❌ **绝对不能删**（存累积依赖历史、RCA 记录、confirmed/refuted 边判定，重建不出来） |
| **ETL Lambda 与其 EventBridge 规则** | ⚠️ **可改，不可删** |
| **EKS 集群本身** | ❌ 不重建 |
| **EKS 里的 petsite 应用** | ✅ **可删可重建**（唯一可重建的对象） |
| Aurora / DynamoDB / S3 / ALB | ❌ 不动 |

**这条约束带来的两个后果**：

1. **ALB 悬空引用债务不会被顺手清掉。** 我此前说「重建能免费还掉那 6 个悬空物理 ID 和 ACM context 债务」——**范围收窄后这条不成立了**，因为不删 `ServicesEks2`。`cdk deploy ServicesEks2` 仍需永久带 `--context acm_certificate_arn=<a661c9dd…>`。
2. **上游的 ECS 部署层根本不用移植。** 既然只重建 EKS 里的应用，那对 `pet-search`/`petfood`/`petlist-adoptions`/`pay-for-adoption` 这四个上游已搬到 ECS 的服务，我们**只移植应用代码，继续用本地的 `eks-service.ts` 构造**。这大幅降低了我原先估的「为四个服务重写部署层」的工作量——**不是重写，是不移植**。

### Phase 1 — 必须存活清单 + 差异清点　【3h】

产出一份逐项决断的清单，这是后面所有阶段的依据。

| 本地独有成果 | 建议处置 | 理由 |
|---|---|---|
| **keep-alive 修复**（`petlistadoptions-go/repository.go`，实测 1.94→143.64 请求/连接，**74 倍**） | **保留 Go 实现，只移植功能变更** | 上游已把该服务用 Python 重写成 `petlistadoptions-py`，我们的修复在上游**无对应文件**。改用 Python 等于丢掉一个已实测的成果并重新引入风险 |
| CPU request/limit 右调（petsite 原本**完全没有 request**） | 保留 | 上游未必有；`petsite-hpa` 失效 155 天靠它才生效 |
| t4g.xlarge 节点组 | 保留 | 与 arm 约束一致 |
| 5 个 PDB | 保留 | 排空期间实测起了作用 |
| search-service 探针（`startupProbe` 5s×30；实测启动 **32.98s** vs 原 `initialDelaySeconds=30`） | 保留 | 旧 Pod 80 分钟内真的重启 3 次，不是理论风险 |
| **`SearchController` 的 1% 故障注入** | **保留**（用户明确要求） | demo 刻意设计 |
| ALB / ACM context 债务 | 不动 | 用户明确不修 |

**同时要定的一个决策**：是否采用上游的 `src/` 目录布局？
**建议不采用**——改布局要动所有 CDK 路径、部署机脚本、CI 引用，换来零功能收益。把上游的应用代码移植进现有 `PetAdoptions/` 目录即可。

### Phase 2 — 图契约扩展 + ETL 改造　【6h】　（可与 Phase 3 并行）

这是被原任务设定低估的部分——它不是收尾动作，而是「图数据库能记录 agent」的**前置**。

契约 `profiles/graph_contract.yaml` 现为 **33 节点 / 26 边类型**，`GRAPH_CONTRACT_MODE` 默认 `enforce`。agent 相关类型**一个都不在里面，ETL 会直接拒写**。

- 新增节点类型：`AgentRuntime` / `AgentTool` / `KnowledgeBase` / `AgentGateway` / `AgentMemory` / `Guardrail`　【1h】
- 新增边类型：`Invokes`（Agent→Tool）/ `Delegates`（Agent→Agent）/ `Retrieves`（Agent→KB）　【1h】
- 新 ETL `etl_agentcore`：从 `bedrock-agentcore-control` 的 list/get API 建资源节点，从 `aws/spans` 建调用边　【3h】
- **身份键钉在 AWS 侧标识**（agent ARN / model ID / KB ID），**不用 `gen_ai.*` OTel 属性**——后者 stability 全是 `development`，与「身份键必须不可变」契约硬冲突　【已决，含在上面】
- **迁移期间先把 5min/15min 的 ETL 规则改为 disabled**（`events disable-rule`，是修改不是删除），重建完再启用并做一次干净全量　【1h】

> 不停 ETL 的代价：迁移期间它会持续把过渡态写进图里，最后要花更多力气清理这些噪声边。

### Phase 3 — PetSite 应用追平　【10h】

> ⚠️ 已知的部署机纪律：`npx` 不在 SSM 默认 PATH（在 nvm 目录）；多行 SSM 命令须用 `--cli-input-json`；git 操作需 `-c safe.directory`；长任务用 `setsid nohup` 再轮询。

### Phase 4 — AgentCore 部署　【8h】

- 移植 6 个 CDK 构造（`waggle-ai-agents-{runtime,gateway,memory,guardrail,autoreload}.ts` + `waggle-ai-nutrition-kb.ts`）　【4h】
- **模型改区：设 5 个环境变量**（见验证 3 的映射表）　【0.5h】← 便宜的部分
- nutrition KB：S3 Vectors + `setup_kb.py` 灌 10 篇知识文档，照 `gp-incident-kb` 的既有范式　【2h】
- **Gateway 打集群内 ClusterIP 服务**：五服务全是 ClusterIP。此前已核实「VPC Lattice 能让 Gateway 直连 ClusterIP」是 **NOT FOUND**，官方只说「私有 MCP server / 内部 REST API / 数据库」。可用现成的 internal ALB `petsite-internal-lt`（`:80`→petsite、`:8081`→search-service），或自建 MCP server 适配层　【1.5h】

> agent 本身跑在 **AgentCore Runtime**（`waggle-ai-agents-runtime.ts` 有 44 处 agentcore 引用），**不是容器**，所以「不能跑 ECS」的约束对 agent 部分天然满足。

### Phase 5 — 观测部署　【4h】

- ✅ **Transaction Search 已开**（2026-09-04 08:49:33Z ACTIVE，索引 1%，head sampling 保持 0.05）——硬前置已满足
- Runtime 的 span log group `/aws/bedrock-agentcore/runtimes/<id>-<endpoint>` **自动建**；**Memory / Gateway / 内置工具的不自动建**，要手工配　【1.5h】
- agent 进程内埋点用 **ADOT SDK**——**ADOT Collector 不支持 agent observability**，集群里那 4 个 `aws-otel-collector` sidecar 复用不了　【1.5h】

> **顺序修正**：原任务设定是 部署→压测→确认→**再**部观测。改为 **部署→观测→压测**——没有观测就无法判断「为什么不正常」。

### Phase 6 — 压测 + 图谱验收　【4h】

- **先设 Bedrock 成本闸**（原设定完全缺失这一项）：`让 loadgen 打 agent 等于用压测放大按量账单`。需 Budgets 告警 + 并发/速率上限　【1h】← **必须在 loadgen 碰 agent 之前**
- 教 loadgen 新端点（petfood / agent 路径）　【1h】
- 重启 ETL，做一次干净全量重建，核对图谱与实际系统一致　【1.5h】
- **TS 验证并入验收**：用比 52/49 计数对比更强的判据——重建后我们**知道**应有哪些服务，检查 `GetServiceGraph` 是否全部出现即可　【0.5h】
