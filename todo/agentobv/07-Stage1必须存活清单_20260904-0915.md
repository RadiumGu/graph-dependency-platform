## 一、本轮查出的三个改变计划的事实

### ① 上游的 arm64 全在 agent 与镜像构建流水线，**与 EKS 节点组无关**

8 处命中逐条核对：

```
waggle-ai-agents-autoreload.ts:79   architecture: Architecture.ARM_64        （Lambda）
waggle-ai-agents-runtime.ts:7       "One containerized agent (Python, ARM64) on Bedrock AgentCore"
stages/containers.ts × 6            多架构镜像构建（AMD64/ARM64）流水线
```

**两个推论**：
- 上游**没有** arm EKS 节点组——「节点全 arm64」是**本地独有资产**，必须保留。
- 但上游的 `stages/containers.ts` 有**成熟的多架构镜像构建流水线**，而本地是手工在部署机上构建。**这一项值得反向采纳**——它能从根上解决我们反复踩的 arm64 镜像构建问题（此前为此把 `cdk-ecr-deployment` 从 3.3.1 升到 4.2.57）。

### ② 上游仍保留 2 个 EKS 构造，但微服务已走 ECS

```
src/cdk/lib/constructs/eks-deployment.ts
src/cdk/lib/constructs/eks.ts
```

但 `pet-search` / `petfood` / `petlist-adoptions` / `pay-for-adoption` 的构造里 **ECS 命中 4–7 处、EKS 命中 0**。所以上游的 EKS 构造是遗留或另有用途。

**结论不变**：继续用**本地的 `eks-service.ts`**——它已加了探针调优 props（`startupGraceSeconds`/`probeTimeoutSeconds`）与 request/limit 拆分，比上游成熟。

### ③ 1% 故障注入在上游**仍然存在**，我上一轮的判断是错的

上一轮我 grep `createBucket` 在上游返回空，据此以为上游删了故障注入。**重查后：`SearchController.java` 在上游存在，且注入逻辑仍在（4 处命中）**——只是实现方式变了，不再叫 `createBucket`。

**影响**：用户要求「保留 demo 刻意注入的 1% 故障」在移植后**天然满足**，不需要额外保护动作。但**要核对上游的注入率是否仍是 1%**——若上游改了比率，需要按用户要求调回。

> 这是本轮第 4 次「grep 未命中 ≠ 事实不存在」。前三次：误判 78 条边阻塞、误判 `disrupt-vpc-endpoint` 可用、误判 FIS 做不了 agent 注入。**纪律：单个关键词 grep 返回空时，必须先确认文件存在、再换关键词，不能直接下「不存在」的结论。**
