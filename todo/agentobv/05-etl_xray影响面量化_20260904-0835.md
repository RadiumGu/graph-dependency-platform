# etl_xray 的 Transaction Search 影响面量化（第 1 步产出）

**日期**：2026-09-04 08:35 UTC
**任务**：读 `etl_xray` 源码，量出开启 CloudWatch Transaction Search 对它的真实影响面。
**结论**：**影响面比我原先写的窄得多，而且前提被推翻了——Transaction Search 在 ap-northeast-1 根本还没开。** 残余未知收窄到一个问题，并有一个廉价可逆的实测方案。

## 一、前提核实：Transaction Search 当前没开

**[实测]** 2026-09-04 08:31，ap-northeast-1：

```bash
$ aws xray get-trace-segment-destination --region ap-northeast-1
{
    "Destination": "XRay",        # ← 不是 CloudWatchLogs，即 Transaction Search 未启用
    "Status": "ACTIVE"
}

$ aws xray get-indexing-rules --region ap-northeast-1
{
    "IndexingRules": [{
        "Name": "Default",
        "Rule": { "Probabilistic": { "DesiredSamplingPercentage": 0.0 } }
    }]
}
```

`Destination: XRay` 就是经典路径（段直接进 X-Ray），`CloudWatchLogs` 才是 Transaction Search 的目的地。所以此前记录的「Transaction Search 因可能影响 etl_xray 而刻意未翻」**状态属实**，它一直没开。

> 附注：`get-indexing-rules` 返回的 `Default` 规则 `ModifiedAt` 是调用当时的时间戳。这两个命令都是 `get`（只读），**我没有启用任何东西**；该时间戳应是 API 在首次读取时惰性物化默认规则所致，属 API 行为而非配置变更。

## 二、`etl_xray` 的 X-Ray 调用面：只有一个 API

**[实测]** `infra/lambda/etl_xray/neptune_etl_xray.py`（861 行）全文检索，X-Ray 相关调用只有三处：

| 行 | 内容 | 性质 |
|---|---|---|
| 94 | `xray_recorder.configure(context_missing='LOG_ERROR')` | 自身埋点，不是取数 |
| 246 | `xray = boto3.client('xray', region_name=REGION)` | 建 client |
| **268** | **`paginator = xray.get_paginator('get_service_graph')`** | **唯一的取数调用** |

**它不调用**：`get_trace_summaries`、`batch_get_traces`、`get_trace_graph`、任何 `get_insight*`。

这一点是全部结论的支点——因为「索引一定百分比的 span 作为 trace summary」直接影响的正是 `GetTraceSummaries` / `BatchGetTraces` 这条链，而 `etl_xray` 一条都没用。

### 调用形态

```python

XRAY_LOOKBACK_HOURS = int(os.environ.get('XRAY_LOOKBACK_HOURS', '24'))  # 第 108 行
```

24 小时回看被切成 4 个 6 小时窗口，逐窗口分页调 `get_service_graph`。单窗口失败只 `warning` 跳过（注释写明理由：合并语义下少一段只是覆盖面变窄，抛出去会让已拿到的其他段白跑）。

## 三、它消费哪些字段：只有拓扑，不含任何度量

**[实测]** 从 `get_service_graph` 返回里实际取用的字段：

| 字段 | 用途 |
|---|---|
| `Services[].Name` | 节点名 → 经 `_classify` 与 `service_mappings.json` 映射到图谱节点 |
| `Services[].Type` | 节点分类（`service` / `resource` / `aws_service` 三分） |
| `Services[].ReferenceId` | 建 `by_ref` 索引，用于把边的目标解析成服务条目 |
| `Services[].Edges[].ReferenceId` | **边的目标** → 产出 `Calls` 边 |

**明确不消费**：`SummaryStatistics`、`ResponseTimeHistogram`、`DurationHistogram`、单条 trace、annotations、metadata。

**[实测]** 实调确认 `SummaryStatistics` 确实存在于返回中（`是否带 SummaryStatistics: True`），但 ETL 不读它。

> 这一条把风险面进一步收窄：即使 Transaction Search 影响了度量类字段的精度（因为度量本可能基于采样计算），`etl_xray` 也不受影响——它只要拓扑。

**复现命令**（开启 TS 后用同一条对比）：

## 五、残余未知：一个问题，官方没有直接答案

**问题**：开启 Transaction Search 后，`GetServiceGraph` 返回的拓扑是否会因为「只索引一定百分比的 span 作为 trace summary」而变少？

**官方给了两条间接证据，指向「不会」**：

**[官方文档]**
> "By default you will also **index 1% of ingested spans for free as trace summary for analysis**, which is typically sufficient given you already have **full end-to-end trace visibility on all ingested spans through Transaction Search**."
> — https://docs.aws.amazon.com/AmazonCloudWatch/latest/monitoring/Enable-Lambda-TransactionSearch.html

即：100% 的 span 都有完整可见性（作为结构化日志），索引百分比只影响「trace summary 分析」这一层。

**[官方文档]**
> "X-Ray processes the data to generate **a service map and searchable trace summaries**."
> — https://docs.aws.amazon.com/lambda/latest/dg/services-xray.html

service map 与 trace summaries 被描述为处理的**两个独立产物**，索引百分比作用于后者。

> ⚠️ **NOT FOUND**：没有找到任何一处官方文档**明确说** `GetServiceGraph` / service map 不受 trace indexing rate 影响。上面两条是间接推论，**不能当作已证实**。已尝试的检索词：`Transaction Search service map GetServiceGraph indexing percentage affect`、`trace indexing rate service graph impact`。

**[第三方]** 有一篇 classmethod 的实测文章专门查「Transaction Search 的 trace indexing rate 是否影响 CloudWatch Application Signals」，其关切是「Application Signals 的指标计算会不会用到更少的 trace」——**这是 Application Signals 而非 `GetServiceGraph`**，不能直接套用，但说明「索引率影响下游派生物」这个担心在业界是真实存在的。

## 六、影响面的最终判定

| 维度 | 判定 | 依据 |
|---|---|---|
| API 面 | **极窄** —— 只 `GetServiceGraph` 一个 | [实测] 源码全文检索 |
| 受索引百分比直接影响的 API | **零个** —— 不调 `GetTraceSummaries` / `BatchGetTraces` | [实测] 同上 |
| 字段面 | **只取拓扑**（Name/Type/ReferenceId/Edges），不取任何度量 | [实测] 源码 + 实调确认 |
| 当前 TS 状态 | **未启用**（`Destination: XRay`） | [实测] |
| 残余风险 | **一个**：service map 是否受索引率影响 | [官方文档间接指向「不会」，但无明文 → NOT FOUND] |
| 成本影响 | **需单独评估**：TS 会把 100% span 作为结构化日志按 CloudWatch 定价计费 | [官方文档] |

**修正我在 `02` 里写的说法**：原文写「如果 `etl_xray` 依赖的是 X-Ray 的 trace summary / service graph，那么索引百分比若设得低，它能看到的依赖证据就会变少」——这个「如果」现在有答案了：**它只依赖 service graph，不依赖 trace summary**。所以风险从「两条链都可能受影响」收窄到「一条链，且官方间接证据指向不受影响」。

## 七、下一步：一个廉价可逆的实测

残余那一条不该靠推理解决，也不值得为它卡住整个方案。做法：

1. **记录基线**（已完成，见第四节）。同时记录压测机状态。
2. **开启 Transaction Search，索引百分比设 1%**（官方免费额度）。用 `aws xray update-trace-segment-destination --destination CloudWatchLogs`。
3. **等一个完整的 `XRAY_MAX_WINDOW_SECONDS` 周期**（6 小时）后，用第四节的复现命令取同等窗口，对比 Services/Edges 数与 Type 分布。
   - 若基本不变 → 残余风险清零，可继续推进 agent 观测方案。
   - 若显著变少 → 把索引百分比提到 100% 再测一次，区分「是索引率造成的」还是「是摄入模式切换造成的」。
4. **可逆性**：`update-trace-segment-destination --destination XRay` 可切回。**但要注意**：切换是账号级的，切回之后 `aws/spans` 里已产生的日志与费用不会回退。
5. **同时量成本**：开启后观察 `aws/spans` 日志组的 `IncomingBytes`，按 CloudWatch Logs 定价外推月成本。参照本环境已有的量级——EKS audit 日志曾实测约 1.9 GB/天 ≈ $45/月。

**顺带一个收益**：`etl_xray` 只用 `GetServiceGraph` 意味着，如果将来 service map 真的退化，还有一条替代路径——Transaction Search 会把 100% 的 span 以 semantic convention 格式存进 `aws/spans` 日志组，可以改从那里读拓扑。这条替代路径的存在让开启 TS 的风险进一步下降，因为**最坏情况有退路而不是死路**。

# 定论（2026-09-04 10:36）：根因是索引率，非摄入模式切换

| 时点 | destination | 索引率 | 1h 窗口 |
|---|---|---|---|
| 08:42Z | XRay | 0% | **52 / 49** |
| 09:51Z | CloudWatchLogs | **1%** | **30 / 26**（丢 55.1%） |
| 10:36Z | CloudWatchLogs | **100%** | **53 / 50**（完全恢复） |

前提校验全部通过（压测机始终 `running`、head sampling 始终 `0.05`）。
6h 窗口在 100% 下为 73 / 84，**0 丢失且净增**。

**`GetServiceGraph` 的覆盖面由 trace summary 索引率驱动。** 1% 时低频事件驱动组件
（StepFn 三个 Lambda、S3、STS、StateMachine）从服务图消失；100% 时全部回来。
它们在两种索引率下**都存在于 `aws/spans`**（100% 摄入），这是排除「采样稀疏」解释的关键证据。

## 这推翻了本文档第五节的推断

第五节基于两条官方间接证据推断「service map 与 trace summaries 是独立产物，
索引率应不影响 service map」，并**明确标了 NOT FOUND（没有官方明文）**。
实测把它推翻了。**幸好当时没当成已证实** —— 否则 14:49Z 之后 `etl_xray` 会静默少建约 27 条边。

## 处置

- 索引率**保持 100%**，head sampling 保持 `0.05` 不动（两个独立旋钮）
- **14:49Z 截止点已解除**，无需改 `etl_xray` 从 `aws/spans` 读拓扑
- ⚠️ **留档警告**：任何人下调索引率都会静默削弱依赖图谱，症状是「边悄悄变少」而非报错。
  `etl_xray` 只有 `GetServiceGraph` 一个源，无法交叉验证。若将来为省成本要下调，
  必须先把它改成从 `aws/spans` 读拓扑。

## 方法论价值

这件事能被查出来，**全靠开启前那份含完整服务集合与边集合的基线快照**。
只存计数的话，看到的只是「52→30」，无法区分「组件消失了」与「本来就没有」——
而正是丢失明细（StepFn/S3/STS 这些**低频**组件）指向了「索引采样」这个假设，
再用 `aws/spans` 里它们的存在证伪了「采样稀疏」，才锁定索引率。

## 决定性测量：根因是**索引率**，不是摄入模式切换（2026-09-04 10:35Z）

### 判定

**索引率。** 把 `Default` 索引规则从 1% 提到 100%（09:52:32Z，head sampling 保持
0.05 未动）后，1h 窗口的服务图**回到了 pre-TS 基线**：

| 时点 | dst | 索引率 | 1h 窗口 | 相对基线 |
|---|---|---|---|---|
| 08:42Z `before` | XRay | — | **52 / 49** | 基线 |
| 09:51Z `after` | CloudWatchLogs | 1% | **30 / 26** | 丢 55% |
| 10:35Z `idx100` | CloudWatchLogs | **100%** | **53 / 50** | **+1 / +1** |

### 计数回到基线不是证据 —— 集合差集才是

计数相同不代表内容相同，所以判据取**集合**。`after → idx100` 的 1h 差集：
**丢失 0，新增 23 个服务 / 24 条边**，其中 **22 个服务、23 条边在 pre-TS 基线里都存在**。
恢复的正是此前报告丢失的那批低频事件驱动组件，逐个对上：

- StepFn 三个 Lambda，每个 3 个条目（`None` / `AWS::Lambda` / `AWS::Lambda::Function`）= 9 个
- `StepFnStateMachine76D362E8-3jkn8j2OUpdQ|AWS::StepFunctions::StateMachine`
- `STS|AWS::STS`，及 `PetSearch -> STS`、`PetSite -> STS` 两条边
- 三个 ETL Lambda（`neptune-etl-from-aws` / `-deepflow` / `-xray`）各 3 个条目 = 9 个
- `search-service` / `pethistory-service` 两个 `remote` 端点

唯一一个「基线没有、现在有」的是 `payforadoption -> 9dw5r2dqlb.execute-api…|remote`，
属新出现流量，与本实验无关。

**这是判别性的**：若根因是摄入模式切换本身，提索引率不会让任何东西回来。
23 个新增里 22 个精确命中 pre-TS 集合，只能由索引率解释。

### 残留 3 个服务 / 4 条边未回到 1h 窗口 —— 已排除，是窗口抖动

`idx100` 的 1h 窗口相对基线仍缺 `S3|AWS::S3`、`sql.conn.exec|remote`、
`sql.conn.reset_session|remote` 及 `PetSearch -> S3`、`payforadoption -> DynamoDB` 等 4 条边。
**同一次快照的 6h 窗口里这三个服务与四条边全部存在**，所以不是丢失，是它们的调用频度
低于 head sampling 0.05 在单个 1h 窗口里的可见门槛。另有一个混淆项：测量点 10:35Z 时
1h 窗口的前 16 分钟（09:36–09:52）仍是 1% 索引的数据，窗口并非纯 100%。
→ 已排定 10:53Z 后取纯 100% 窗口的确认快照 `idx100_clean`（见文末）。

### 副产品：post-TS 的 `GetServiceGraph` 会返回重复条目

`service_count`（原始列表长度）与去重后的集合大小在 post-TS 快照里不再相等：

| 快照 | 1h 原始/去重 | 6h 原始/去重 |
|---|---|---|
| `before` | 52 / 52 | 52 / 52 |
| `after` | 30 / 30 | 69 / **55** |
| `idx100` | 53 / 53 | 73 / **56** |

只在**跨越 destination 切换时点的 6h 窗口**里出现，1h 窗口和纯 pre-TS 的 6h 窗口都没有。
最可能的解释是该窗口同时命中 XRay 与 CloudWatchLogs 两个后端的图片段，同一逻辑服务
各出一次。窗口全部滑过 08:49Z 后应自行消失（待 14:49Z 后复核）。
**影响面**：`etl_xray` 按 name 建节点、写入是 upsert，重复条目会合并，不产生重复节点；
但**任何直接引用 `service_count` 的计数都会在过渡期虚高**，本文档此前的计数已改用去重值。

### `etl_xray` 实际产出未下滑 —— 反而在涨

```
08:00Z  xray_nodes_seen 32 / xray_edges_seen 25   ← pre-TS 基线
09:00Z  xray_nodes_seen 33 / xray_edges_seen 26
10:00Z  xray_nodes_seen 34 / xray_edges_seen 28
```

三轮 `edges_write_failed 0`、`edges_deactivated 0`，`edges_corroborated` 24→25→26。
**没有开始丢边**，原因是回看窗口 24h 目前绝大部分仍是 pre-TS 数据 —— 这正是 14:49Z

### 成本提示

索引率 100% 意味着 TS 按 100% 的 span 计费索引，而非 1%。head sampling 仍为 0.05，
所以进入 TS 的 span 量本身只有全量的 5% —— 100% 索引作用在这 5% 上。若后续要压成本，
**正确的旋钮是 head sampling（`FixedRate`），不是索引率**：前者等比减少所有服务的 span，
后者会**选择性地让低频组件整体消失**，而 `etl_xray` 的价值恰恰在这些低频边上。

#### 但有一个副作用需要修：不透明标签的护栏被 type 绕过了

`XRAY_OPAQUE_LABELS` 的拦截写在 `if xray_type == 'remote':` 分支内部
（`neptune_etl_xray.py:499`），而 `sql.conn.exec` 现在的 type 是 `Database::SQL`，
**不再走那个分支**，护栏被绕过。

当前行为仍然正确 —— 落到末尾的 `return None`（`:519`，「刻意跳过而不是猜一个节点类型」），
所以**没有造出假节点**，`edges_skipped_no_node` 从 1 升到 2 即此。但性质变了：
它们从「已识别的、刻意丢弃的不透明标签」变成了「未映射的未知类型」，被计入
`xray_unmapped_types`，而那个字段的语义是**「应当补映射的类型」**。信号被污染了。

**修法**：把 `XRAY_OPAQUE_LABELS` 的判定按**名字**前移到 type 分支之外。
优先级低（不影响正确性，只影响信号纯度），但要在下轮改 `etl_xray` 时一并做。

#### `Database::SQL` 不要映射成节点

它的 Name 是 `sql.conn.exec` / `sql.conn.reset_session` —— SDK 给 subsegment 起的**操作名**，
不是资源标识。X-Ray 仍未给出 Aurora 集群标识，所以 TS 在这里只是把 `remote` 换成了
`Database::SQL`，**粒度并没有变细**。按 `XRAY_OPAQUE_LABELS` 继续丢弃是对的。
