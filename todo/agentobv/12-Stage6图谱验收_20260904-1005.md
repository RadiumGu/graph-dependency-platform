但属于既有问题，与本轮六个 Stage 无关。**未修，已记录。**

### 又一次假推断：`总数 - active ≠ 失活`

我先前统计出「`DependsOn` 总 21 / active 1 / 失活 20」，据此以为有 20 条边失活。
但直接查 `has('active', false)` 返回 **0**。

**那 20 条边根本没有 `active` 属性** —— 契约里 `active` 明确只适用于 dynamic 边
（「`active(bool)`: dynamic 边是否仍被观测到」），静态边（`etl_aws`/`etl_cfn` 从模板
声明出来的）本就不该有。

**本轮第 7 次自己的工具产生假警报。** 教训在累积：
- 单行 grep 遇跨行写法 → 假阴性
- 正则漏掉无注释行 → 假阴性
- 两套命名体系直接对比 → 假不匹配
- **可选属性上做 `总数 - 有值数` → 假失活**

## 四、✅ 补完 `etl_xray` 的契约门禁（Stage 2 承诺推到本 Stage 的事）

### 修的是什么

`profiles/graph_contract.yaml` 开头写着「合法的 source 取值词表，**由
`graph_contract.assert_source()` 在写入时强制**」。而实测：

```
etl_aws        4 个文件引用门禁 ✅
etl_cfn        3 个文件引用门禁 ✅
etl_deepflow   1 个文件引用门禁 ✅
etl_xray       0 个文件引用门禁 ❌   ← 契约声称强制，但这条路径完全没接
```

契约当初就是为「四个写入 ETL 无一校验节点/边类型」而建的 —— **修了三个漏了一个。**

### 怎么修的

在 `neptune_etl_xray.py` 加了 8 个门禁调用点：

| 位置 | 门禁 |
|---|---|
| `upsert_aws_service_endpoints` 的**循环内** | `assert_node_type('AWSServiceEndpoint')` + `assert_source('xray', ...)` |
| `upsert_xray_edges` 的**循环内**（`edge_type` 确定后） | `assert_edge_type(edge_type)` + `assert_source('xray', ...)` |

**两个设计决定**：

1. **门禁放在循环内而非函数头** —— 门禁是**按写入项**校验的。提到函数外就变成
   「只要有一项合法就全放行」，那是无门禁状态的翻版。
2. **`assert_edge_type` 只传 label，不传 src/dst** —— 本 ETL 的端点匹配是多标签 `or`
   子句（`_src_label_clause` / `_dst_matcher`，一个 Microservice 可能同时匹配
   `LambdaFunction`），运行时无法确定唯一端点标签对。校验「边类型已声明」已能挡住
   拼错与新造标签，那是门禁的主要目的。

### 验证

| 判据 | 结果 |
|---|---|
| 编译 | ✅ |
| 本 ETL 实际写的类型全部已声明（否则门禁会当场炸掉每小时跑的生产 ETL） | ✅ `AWSServiceEndpoint` / `LocatedIn` / `Calls` / `AccessesData` / source `xray` 全部通过 |
| **反例确认门禁真生效** | ✅ `NotARealType` 被拒绝 |

> 「本 ETL 实际写的类型全部已声明」这一条是**必须先验的** —— 门禁默认
> `GRAPH_CONTRACT_MODE=enforce` 会抛错，若有任何一个类型未声明，
> 下一次 `neptune-etl-xray-hourly` 触发就会整轮失败。

`etl_trigger` 仍是 0 引用，但它是**触发器、不写图**，不需要门禁。
六个 ETL 里五个写图的现在全部接上了。
