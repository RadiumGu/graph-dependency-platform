### 3.3 推翻原调研文档的一处说法

原 `research-agent-dependency-graph` 文档写：

> "Google GenAI instrumentor 发的是 `gen_ai.system = "gemini"` 而非 `gen_ai.provider.name = "gcp.gen_ai"`" —— 归因为「instrumentor 实现不一致」

**更准确的表述是**：`gen_ai.system` 是**被官方弃用并移出注册表的旧属性**，`gen_ai.provider.name` 是它的替代。所以看到 `gen_ai.system` 不是「实现不一致」，是「用了旧属性」。这个区分影响 legacy-compat 映射表的写法——它是**版本迁移映射**，不是**厂商差异映射**。

### 3.4 instrumentor 不一致确有其事，且有真实 issue 佐证

已核实的真实 issue：**litellm #36759 / #36779 / #36863**、**traceloop #3515**。

> ⚠️ **NOT FOUND**：OTel 官方 semconv 仓**自身**登记的 instrumentor 不一致 issue（已尝试多组检索词）。上述 issue 都在各 instrumentor 自己的仓库里。

### 3.5 这对本项目契约的直接冲击（重要）

本项目契约有一条硬约束：**身份键必须不可变**（`profiles/graph_contract.yaml` 的 `immutable` 字段 + 守门测试）。

而 `02` 方案里提议用 `gen_ai.agent.id` / `gen_ai.tool.name` / `gen_ai.conversation.id` 做身份键 —— **这三个的 stability 全是 `development`，规范层面就可能变**。

**处置建议**：不要直接把 OTel 属性当身份键，而是：
- `Agent` 用 **AgentCore 分配的 agent ARN/ID**（AWS 侧标识，比 OTel 属性稳定）
- `Model` 用 **Bedrock model ID**（AWS 侧标识）
- `KnowledgeBase` 用 **Bedrock KB ID**
- 只有 `Tool` / `Session` 不得不依赖 OTel 属性 —— 这两个要在契约里显式标注「身份键来自 development 状态的规范」，并加守门测试监控取值形态变化

> 这与本项目已记录的模式一致：**缺陷集中在「身份不唯一」这一类**（EC2 双节点、SSM/SimpleSystemsManagement、search-service/petsearch 三次）。在 agent 场景提前把身份键钉在 AWS 侧标识上，是避免第四次的最低成本做法。

## 四、Agent 的证伪：注入侧没有 AWS 原生能力，判定侧有

### 4.1 注入侧：FIS 没有 GenAI **action**，但 FIS **能且应该**做 agent 注入

> ⚠️ **本节的结论已于 2026-09-04 08:25 被推翻并重写。原文写的是「所以 agent 侧注入必须走应用层开关……不要指望 FIS」——那是错的。** 推翻依据是 `aws-samples/fis-template-library` 的 `agentcore-strands-agent-faults` 模板，详见 `04-FIS模板库与agent注入_20260904-0830.md`。撤销原因记在此处而不是直接删掉，是为了让「从『没有原生 action』跳到『这条路走不通』」这个推理错误留痕——**这已是同一类错误的第三次**（前两次：误判 78 条托管资源边阻塞在自建 SSM 方案、误判 `disrupt-vpc-endpoint` 可用）。

**仍然成立的部分**：AWS FIS 的 action 清单里**没有任何 Bedrock / AgentCore / GenAI action**（已逐节核对官方完整 action 参考页）。FIS 全部 action 覆盖的服务：Fault-injection（仅 `aws:fis:inject-api-*`）、CloudWatch、DynamoDB、Aurora DSQL、EBS、EC2、ECS、EKS、ElastiCache、Kinesis、Lambda、MemoryDB、Network、RDS、S3、SSM、Direct Connect。

**关键限制**（仍然成立）：通用的 `aws:fis:inject-api-internal-error / throttle / unavailable` **只支持 `ec2` 和 `kinesis` 两个命名空间**，打不了 Bedrock API。
— https://docs.aws.amazon.com/fis/latest/userguide/fis-actions-reference.html

**被推翻的部分**：「没有原生 action」**不等于**「FIS 做不了 agent 注入」。官方样例用的是通用的 `aws:ssm:start-automation-execution` 把 FIS 作为**编排器**，真正的注入点在 agent 进程内（读 SSM Parameter Store 的 plugin）。FIS 提供的是实验生命周期、stop condition 与 `onCancel`/`onFailure` 回滚——这些恰恰是自己攒开关最难做对的部分。

**正确的结论**：agent 侧注入**应该**用 FIS 编排，注入点放在 agent 进程内。完整机制、可复用代码与四个已知陷阱见 `04`。

> 这次错误的教训与本项目已记录的纪律同源：**「某个动作出现在 list-actions 里 ≠ 它在环境里能选出目标」的反面同样成立——「list-actions 里没有 ≠ 这件事做不到」**。判断一个能力是否可得，要枚举到「官方样例怎么组合现有原语」这一层，而不是停在 action 清单。

### 4.2 判定侧：AWS 有两套官方能力

**Amazon Bedrock Evaluations**（GA）—— 评模型输出与 RAG，含 LLM-as-a-judge（2024-12 preview → 现 GA）。作为 job 运行：S3 数据集进、算分回写。

**Amazon Bedrock AgentCore Evaluations**（**GA 2026-03-31**）—— **专门评 agent 行为**，三种方式：
1. **LLM-as-a-Judge**
2. **Ground Truth** —— `expected_response` / `expected_trajectory` / `assertions`
3. **Custom code** —— 用 Lambda 做确定性打分

> `expected_trajectory` 这一项对本项目价值最高：它评的是**agent 走了哪条路径**，而不只是最终答案对不对。这正是「验证一条 `Delegates` / `Invokes` 边是否真实存在」需要的判据形态。

### 4.3 社区指标（非 AWS 官方，按此标注）

- **faithfulness 与 groundedness 是同一指标的不同叫法**（DeepEval 官方明说）
- **Tool-call correctness（DeepEval）**：核心是**确定性**分数，可选叠加 LLM 判「最优性」，**取二者最小值**
- 其余框架：RAGAS / TruLens / Langfuse

## 五、Gateway 进 VPC：能进，但有一处必须修正的细节

**能进 VPC = FOUND**（Amazon VPC Lattice，`privateEndpoint`，仅 MCP server 与 OpenAPI target）。

> ⚠️ **但「直接对准裸 ClusterIP」= NOT FOUND**。官方文档说的是「私有 MCP server、内部 REST API、数据库」这类 VPC 内资源，**没有**任何一处说可以把 target 指向 Kubernetes 的 ClusterIP。

**结论修正**：VPC Lattice 解决的是「不走公网进 VPC」，**不是**「直连 ClusterIP」。PetSite 的五个 ClusterIP 服务前面**仍然需要一个 internal LB**（或一个 VPC 内自建的 MCP server 作为适配层）作为 Lattice 的目标。

这一条已回写进 `01-agent系统接入方案` 的第四节。

不支持矩阵（官方明确列举）：

| target 类型 | `privateEndpoint` 进 VPC |
|---|---|
| MCP server | ✅ |
| OpenAPI 规范 | ✅ |
| Smithy 模型 | ❌ 不支持 |
| API Gateway REST API | ❌ 不能直接进 VPC（需 VPC Link 或导出 OpenAPI） |
