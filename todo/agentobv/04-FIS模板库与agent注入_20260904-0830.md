## 一、先撤销一个错误结论

`03` 原文写：「FIS 没有任何 Bedrock/AgentCore/GenAI action，**所以** agent 侧注入必须走应用层开关……**不要指望 FIS**」。

**前半句对，后半句错。** 官方样例 `agentcore-strands-agent-faults` 就是用 FIS 做 agent 注入的——它不需要原生 GenAI action，用的是通用的 `aws:ssm:start-automation-execution`。

这是同一类推理错误的**第三次**：

| 次 | 错误判断 | 被什么推翻 |
|---|---|---|
| 1 | 78 条托管资源边阻塞在「需自建 SSM 改安全组」 | FIS 原生就有 `pod-network-blackhole-port` 等能力 |
| 2 | `disrupt-vpc-endpoint` 可用于验证 11 条 AWSServiceEndpoint 边 | 该 action 的 targets 是 `aws:ec2:vpc-endpoint`，而被测 VPC 里只有一个无关端点 |
| 3 | **没有 GenAI action ⇒ agent 注入用不了 FIS** | **官方样例用通用 action 组合出了 agent 注入** |

**教训的准确表述**：已知纪律是「list-actions 里有 ≠ 环境里能选出目标」。它的**反面同样成立**——「list-actions 里没有 ≠ 这件事做不到」。判断能力是否可得，要枚举到「官方样例怎么组合现有原语」这一层，不能停在 action 清单。

## 二、这个模板的机制（这是最有价值的部分）

```
FIS 实验（单个 aws:ssm:start-automation-execution 动作）
  └─→ SSM Automation 文档 ChaosExperiment
        ① Enable：写 /chaos/{runtime_id}/{fault_rate, fault_injections, execution_id}
                   然后【最后】才写 active=true —— 保证没有任何一次调用看到半写状态
        ② Hold：保持 DurationSeconds
        ③ Disable：【先】写 active=false（关闭开关），等 15 秒 TTL，【再】删除四个参数
        ④ Rollback：③ 挂在 onCancel / onFailure 上
                    stop-condition 告警触发 → FIS 取消执行 → 写 active=false → 清理

agent 侧（进程内，不经网络代理）
  └─→ vendored 的 strands_agentcore_chaos.py
        plugins=chaos_plugins() 返回两个 plugin：
          · RuntimeChaosController —— 读 SSM 配置（TTL 10s 缓存），决定本次调用是否武装故障
          · ChaosPlugin（来自 strands_evals，未改动）—— 执行真正的 tool 级注入
```

**注入点是 tool 边界**——`fault_rate` 决定「这次调用是否被注入」，`fault_injections`（tool → 效果的 JSON map）决定「注入什么」。

### 支持的效果类型

**Pre-hook（tool 根本不执行，agent 直接收到错误结果）**：

| `effect_type` | 模拟 |
|---|---|
| `timeout` | tool 调用超时 |
| `network_error` | 到 tool 的网络故障 |
| `execution_error` | tool 执行中失败 |
| `validation_error` | tool 拒绝其输入 |

**Post-hook（tool 正常执行，然后在 agent 看到之前污染结果）**：

| `effect_type` | 做什么 | 参数 |
|---|---|---|
| `truncate_fields` | 截断结果字段值 | `max_length`（默认 10） |
| `remove_fields` | 随机删掉部分结果字段 | `remove_ratio`（默认 0.5） |
| `corrupt_values` | 随机污染部分结果值 | `corrupt_ratio`（默认 0.5） |

效果定义的权威来源是 `strands_evals.chaos.effects`，新效果类型会被自动识别。

### 它的假设写得很准，值得照抄

> "When tool calls made by a Strands agent are **cancelled** or its tool results are **corrupted**, the agent will detect that a trustworthy result is unavailable and **fail safe** ... **rather than fabricate a result from missing data**."

「不要凭缺失数据编造结果」正是 agent 故障与微服务故障的本质差别——这也是本项目此前给 DevOps Agent 加 Evidence integrity 规则时踩过的同一个坑（agent 编造了 CWAgent 指标值）。

## 三、四个必须知道的陷阱（三个会产生假 PASS）

### 陷阱 1：tool 名不匹配 → 实验「成功」但零注入 ⚠️ 最危险

README 原文：

> "The shipped template's default (`get_move`, `get_pokemon`) targets a demo agent's tools. Tool names are matched exactly against your agent's tools, and **a name that matches nothing injects nothing: run the template unmodified against your own agent and the experiment will complete "successfully" while injecting no faults at all.**"

**这是一台假 PASS 生成器**，而且与本项目已经踩过的坑完全同形：
- T-214h：Phase 5 判出假 `PASSED`
- `petsearch->s3`：X-Ray 严格按故障窗口复核后显示**注入未生效**，一度误判 confirmed

**处置（必须做，不是可选）**：本项目的「注入生效门禁」要为 agent 场景增加两条判据，缺一不可：
1. `aws ssm get-parameters-by-path --path "/chaos/<runtime_id>/"` 确认 `active=true` 与 `fault_injections` 已写入
2. **确认至少出现过一条 `activated chaos execution=<...> tools=<...>` 日志**

只有两条都满足，才允许接受 confirmed / refuted 判定。否则一律记为 `inconclusive（注入未生效）`。

### 陷阱 2：`maxDuration` 小于 `DurationSeconds` + 15s → 实验窗口静默截断

> "it must exceed `DurationSeconds` plus the 15-second TTL wait. If it does not, FIS cancels the automation mid-hold. The rollback path still disables chaos safely, but **your experiment window silently truncates.**"

模板默认 `maxDuration = PT20M`、`DurationSeconds = 900`。改 duration 时必须同时改 `maxDuration`。

> 这与本项目已记录的纪律直接呼应：**「缩短注入时长会制造出正好要防的假 refuted」**。这里是同一件事的另一个成因——不是你主动缩短，是 FIS 帮你截断了而且不报错。

### 陷阱 3：runtime ID 解析不一致 → 一个 FIS 实验对不上任何 runtime

controller 按三个来源依次解析 runtime ID：
1. `AGENT_RUNTIME_ID` 环境变量（**推荐**，完全可控且可移植到 ECS/Lambda）
2. `AGENTCORE_RUNTIME_URL`（AgentCore Runtime 设置，runtime ARN 在其 path 里 URL 编码，ID 是 `runtime/` 之后那段）
3. `OTEL_RESOURCE_ATTRIBUTES` 里的 `cloud.resource_id`（**AgentCore observability 开启时存在，默认开启**）

解析不到就**在构造时抛异常而不是猜**（fail closed）。解析出的值必须**等于**传给 `ChaosExperiment` 文档的 `RuntimeId` 参数——这个相等关系就是「一个 FIS 实验绑定到恰好一个 runtime」的全部机制。

> 注意第 3 个来源：**它依赖 AgentCore observability 已开启**。这与 `02` 里 Transaction Search 那条门槛串在了一起——观测没配好，连注入的目标解析都可能落到 fallback 上。

### 陷阱 4（安全，非假 PASS）：必须用专用 chaos runtime

> "A Strands agent integrated with `plugins=chaos_plugins()` ... is built and deployed to a **dedicated chaos** Amazon Bedrock AgentCore Runtime, **separate from production**."

生产构建必须：不含 `strands_agentcore_chaos.py`、不传 `plugins=chaos_plugins()`、其 runtime 执行角色**无** `/chaos/*` 访问权。

**这对 `01` 的方案有直接影响**：如果要做 agent 证伪，需要**两个 AgentCore Runtime**（生产 + chaos），不是一个。这是此前方案里没算进去的成本。

**设计上的一个优点值得学**：fail-closed —— JSON 格式错、未知 `effect_type`、一个 tool 配多个效果、`fault_rate` 越界，全部退化为 no-op。原文：「**A misconfiguration can only ever produce less chaos, never more.**」

## 四、对本项目图谱平台的直接价值

### 4.1 它补上了 `Invokes` 边证伪缺的那块

本项目的证伪方法是「注入故障看依赖是否真实」。对 `Agent → Tool` 的 `Invokes` 边，此前没有可靠注入手段（`03` 原文只能推荐 HTTP 层拦截的 AgentChaos）。现在有了 tool 边界的精确注入，而且：

- `timeout` / `execution_error`（pre-hook）验证**「这条边存在且 agent 依赖它」**
- `truncate_fields` / `corrupt_values`（post-hook）验证**「agent 对这条边的数据质量敏感」**——这是微服务证伪根本没有的维度

### 4.2 `execution_id` 是现成的 provenance 句柄

> "The `execution_id` parameter (the SSM Automation execution ID) correlates CloudWatch Logs, CloudTrail, and FIS entries for a single run."

本项目已有 `ChaosExperiment` 节点与 `TestedBy` 边。`execution_id` 可直接作为 `ChaosExperiment` 节点的身份键——它是 **AWS 侧分配的标识**，符合 `03` 第 3.5 节定的原则（身份键钉在 AWS 侧标识而非 OTel 属性上）。

### 4.3 它印证了本项目关于「判据必须换」的判断

> "Because a tool-level fault that the agent handles gracefully **completes as a successful invocation, it is invisible to infrastructure error metrics.** Surface the agent's own signal instead."

`02` 第五节写的「agent 的故障表现为输出质量下降而非 HTTP 500」，官方模板给出了同样的诊断和一个具体解法：**在 CloudWatch Logs 上对 `activated chaos` 做 metric filter**，用它做告警与画图，而不是看基础设施错误率。

模板的 Next Steps 也把判据方向写明了：**task-success rate / response-quality score / downstream action correctness**，而不是 infrastructure error rate。

### 4.4 需要在契约里加的东西

`02` 第 4.2 节提的节点/边之外，agent 证伪还需要：

| 项 | 说明 |
|---|---|
| `ChaosExperiment` 节点新增属性 | `fault_rate`、`fault_injections`（哪些 tool 被打了什么效果）、`injection_verified`（布尔，对应陷阱 1 的门禁结果） |
| `TestedBy` 边 | 复用现有边类型，源是被验证的 `Invokes` 边所指的 `Tool` 节点 |
| 判定取值 | 现有 `confirmed` / `refuted` / `inconclusive` 够用，但 `inconclusive` 需要能区分「注入未生效」与「注入生效但结论不明」 |

## 六、对方案的净影响

### 加进 `01` 的：
- 若要做 agent 证伪，需要**两个 AgentCore Runtime**（生产 + 专用 chaos），chaos 构建额外含 `strands_evals` + `pydantic` + `boto3`，生产构建必须完全不含且无 `/chaos/*` 权限。

### 加进 `02` 的：
- agent 注入的可观测性判据是 **CloudWatch Logs metric filter on `activated chaos`**，不是基础设施错误率。
- runtime ID 的第 3 个解析来源依赖 AgentCore observability 已开启 —— 与 Transaction Search 那条门槛串联。

### 改写 `03` 的：
- 第 4.1 节的结论已撤销重写（见该节的撤销说明）。
- 资产清单应加入 `aws-samples/fis-template-library`（MIT-0）与 `fis-template-library-tooling`。

### 执行顺序的调整：
`README` 里第 8 步「最后做 agent 侧证伪」要展开成：
1. 部署**专用 chaos runtime**（与生产分离）
2. vendored `strands_agentcore_chaos.py` 并接 `plugins=chaos_plugins()`
3. 建 3 个 IAM 角色（FIS 实验角色、SSM Automation 角色、chaos runtime 执行角色）
4. 部署 `ChaosExperiment` SSM 文档
5. **先把 `fault_injections` 的 tool 名改成本环境真实注册的 tool 名**（否则零注入假成功）
6. **先建注入生效门禁**（SSM 参数 + `activated chaos` 日志双判据），再跑第一个实验
7. 从 `fault_rate` 0.05–0.1 与单个 `timeout` 起步，再升级到 `corrupt_values` 与多 tool
