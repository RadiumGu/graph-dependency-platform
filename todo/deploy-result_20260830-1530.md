# PetSite 追平部署结果（2026-08-30 15:05–15:30 UTC）

**范围**：CDK 与线上追平 + CPU 右调 + 节点组扩容 t4g.xlarge + keep-alive 修复
**结果**：两个栈都 `UPDATE_COMPLETE`，全程零中断，keep-alive 修复效果 74 倍

## 一、部署过程中出的问题（第一次尝试失败）

`ServicesEks2` 第一次部署失败并进入 `UPDATE_ROLLBACK_FAILED`：

```
UPDATE_FAILED | AWS::ElasticLoadBalancingV2::Listener | PetSiteLoadBalancer/HttpsListenerV2
  Listener '...listener/app/Servic-PetSi-by0kpyBtxswj/bbe5082588a126fc/8a1d964dc1c53274'
  not found (HandlerErrorCode: NotFound)
```

### 我在 diff 审阅阶段的判断错在哪

审阅时我看到 `Certificates a661c9dd → ce750241`，判断「模板落后于线上，
线上 :443 已是 ce750241，部署等于对齐模板，对线上无实际影响」。

**证书值那部分是对的，但结论错了**：listener 不是被原地改证书，而是被**删除重建**。
CFN 记录的物理 ID 早已悬空，任何对它的 UPDATE 都必然 NotFound。
我核对了「值是否一致」，没核对「引用是否还有效」。

### 漂移的真实范围（远大于一个 listener）

逐个核对物理 ID 是否真实存在：

| CFN 资源 | CFN 记录的物理 ID | 实际 |
|---|---|---|
| :443 Listener | `...8a1d964dc1c53274` | ❌ 悬空（线上真值 `0efebd189a05b6f7`） |
| :80 Listener | `...db82815d2c93c9b1` | ❌ 悬空（线上真值 `171d62d9cc70c94d`） |
| GrafanaRule | `.../f426621212d1e0e5` | ❌ 悬空 |
| NeptuneUIRule | `.../c6f41eabdca9c145` | ❌ 悬空 |
| PetAdoptionsHistoryTargetGroups | `.../2539d67f360649f2` | ❌ 悬空 |
| StreamlitGraphRule | `.../ba554ff266e913b1` | ❌ 悬空 |

**整个 ALB listener 子树（2 个 listener + 4 条规则）都是在 CloudFormation 之外
被重建的。** 而且线上只有 2 条业务规则（优先级 10、20）+ default，
CDK 里定义了 4 条 —— 规则集本身也不一致。

## 二、为什么没有「彻底修 ALB」

彻底修需要 orphan + re-adopt：把 6 个资源从栈里摘掉、删除线上真实 listener、
再让 CFN 重建。代价是：

1. **入口 ALB 的 HTTPS 会中断**（demo 环境可接受，但压测正在跑）
2. **更关键：路由会变**。CFN 按模板重建会产生 4 条规则，
   而线上现在只有 2 条 —— 这是一次**入口流量的路由变更**

把这个变更作为「节点组扩容」的副作用来做是不可接受的：出问题时无法区分归因，
而且它与本次目标（容量、CPU、连接复用）完全无关。

### 采取的解法

证书来自 CDK context `acm_certificate_arn`（`lib/services-eks.ts:211`），
所以部署时用已部署模板里的旧值覆盖即可，让 CFN 认为 listener 无变化、不去触碰它：

```bash
cdk deploy ServicesEks2 \
  --context acm_certificate_arn=arn:aws:acm:...certificate/a661c9dd-... \
  --require-approval never
```

**仓库里 `cdk.json` 的值保持 `ce750241`（与线上一致，是真话）**，只有这一次部署做规避。

> ⚠️ **后续每次 `cdk deploy ServicesEks2` 都需要这个 context 覆盖**，
> 直到 ALB 漂移被独立修复。这是已知债务，不是遗漏。

# 补记：search-service 探针修复与刻意保留的取值分叉（2026-08-31 02:00–03:15）

## 修的是什么

`search-service` 是这套里唯一的 JVM 服务，实测 `Started Application in 32.98 seconds`，
而 `eks-service.ts` 里四个 EKS 服务**共用**的 `livenessProbe.initialDelaySeconds` 是 30
—— 首次 liveness 恰好在应用起来之前打。HPA 扩容造成 CPU 争抢时必然进重启循环。

**这不是理论风险，是已发生的事故**：

| 时刻 | 观测 |
|---|---|
| 00:39 | `restarts=0`（当时判定「风险未发作」） |
| 02:01 | 同一批 Pod `restarts=3 / 1 / 3` —— 80 分钟里真的循环重启了 |
| 03:13 | 修复后新 Pod 已运行 72 分钟，全 10 个 Pod 合计 `restarts=0` |

## 做法：用 K8s 的正解，且只改被证实有害的那一个

`startupProbe` 成功之前 liveness 与 readiness 都不执行，所以「启动慢」与
「运行中卡死」终于用两组独立参数表达，不再靠一个 `initialDelaySeconds` 兼顾两件事。

因为探针在 `eks-service.ts` 里是四个服务共用的，做成**可选 props**
（`startupGraceSeconds` / `probeTimeoutSeconds`）而非改共用默认值：

```
SearchServiceEks            startupGrace=150 probeTimeout=5   ← 唯一的 JVM 服务
PayForAdoptionServiceEks    未传 → 无 startupProbe，行为不变
ListAdoptionsServiceEks     未传 → 无 startupProbe，行为不变
TrafficGeneratorServiceEks  未传 → 无 startupProbe，行为不变
```

副作用（据实记录）：未传参的服务被显式写上了 `timeoutSeconds: 1`，
那是 K8s 本来的隐含默认值，**行为零变化**，但模板变了会滚动一次 Pod。
实测 `pay-for-adoption` 与 `list-adoptions` 滚动后 `ready=2/2`、无 startupProbe、
`initialDelay=30 timeout=1`，与改动前一致。

## 刻意保留的分叉（**不是待修的漂移**）

```
CDK  (last-applied)  liveness initialDelay 0  / timeout 5
线上 (用户 patch)     liveness initialDelay 60 / timeout 3
```

**用户 2026-08-31 03:13 明确决定：保持 CDK 的 0/5 不动，下次部署就让它覆盖成更宽容的值。**

安全依据（不是「大概没事」）：
- K8s 规定 **startupProbe 成功前所有其他探针都不执行**，所以 liveness 的
  `initialDelaySeconds` 在启动期根本不起作用 —— 0 与 60 等价，保护来自 150s 的 startupProbe；
- `timeoutSeconds` 5 比 3 **更宽容**，覆盖 JVM GC 停顿的余量更大。

所以下次 `cdk deploy ServicesEks2` 把 60/3 覆盖成 0/5 不是退步。
**后续会话不要把这个差异当漂移去追平。**
