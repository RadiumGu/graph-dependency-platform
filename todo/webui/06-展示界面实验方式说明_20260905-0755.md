线上地址：<https://rainmeadows.com/streamlit/>

记录时间：2026-09-05 · 对应代码：`demo/`（10 个页面）+ `mcp/`（AgentCore MCP server）

## 0. 这个界面在回答什么问题

市面上的依赖图都在回答「我看到了什么」。这个平台回答的是**「我看到的是真的吗」**。

所以整个界面的组织方式不是功能目录，而是一条论证链：先给出主张，再用实时数字自证，
再让观众自己去查、自己去验。**首页所有数字都是现算的**，没有一个硬编码——
数据源是 `profiles/graph_contract.yaml`、`QUERY_CATALOG`、`chaos/.../fault_catalog.yaml`
和活图谱本身。

## 2. 两种运行模式，界面会明确告诉你现在是哪种

| 模式 | 触发条件 | 界面表现 |
|---|---|---|
| **实时** | Neptune 可达 | 侧栏「Neptune 已连接」，数字来自活图谱 |
| **离线快照** | Neptune 不可达 | 侧栏「离线快照模式」，页面顶部**明确标注是快照及抓取时间** |

离线快照是 `demo/fixtures/*.json` 里的 8 份**真实**数据，用
`demo/fixtures/refresh_fixtures.py` 从活图谱抓的。**不伪装成实时**——
这是刻意的设计：一个讲「验证」的平台，不能在自己的展示上撒谎。

## 3. 图数据库的展示方式（第 3 页 Graph Explorer）

### 3.1 为什么不直接画全图

活图谱有 **88 个节点 / 146 条边**（1 跳邻域规模），平均度 3.3、密度 0.038——
这是**稀疏图**，不是毛线球。但直接全画依然不可读，原因不是密度，是**认知预算**：

- IEEE TVCG 2020（EEG + 眼动，实测）：节点超过约 **50** 个，判断准确率掉到 **50% 以下**
- 颜色可区分上限约 **7** 类，形状约 **5** 类（arXiv:2103.06084）
- 而契约里有 **39 种节点类型 / 29 种边类型**——**没有任何首屏能一类一色**

调研 10 个成熟产品（Grafana、Datadog、Dynatrace 等）的共同做法也一致：
**从不渲染全图**，一律锚点 + 有界邻域 + 渐进展开；分层布局优先，
力导向只在 500+ 节点时才建议。

> 顺带纠正一个常见误解：「邻接矩阵优于节点链接」（Ghoniem 2004）只对**密集**图成立。
> Okoe/Jianu/Kobourov 2017 用 557 名被试在 258 节点**稀疏**图上做对照，结论相反——
> 稀疏图上节点链接**胜过**矩阵，因为「空矩阵和满矩阵占一样大的地方」。
> 所以这里不做矩阵视图。

### 3.2 实际采用的六条策略

1. **锚点 + 跳数**，默认 1 跳。4 个预置场景各自带锚点，各回答一个具体问题。
2. **边语义分流**。契约的 `dependency: true` 把 29 种边分成 **6 种依赖边**（画箭头）
   和 **23 种结构边**（包含关系）。**默认只画 6 种依赖边**——结构边是杂乱的主因，
   需要显式勾选才出现。这一个字段同时解决了「颜色不够用」和「看起来乱」。
3. **分层布局**，方向 = 依赖方向（上游在上 → 锚点 → 下游在下），
   按**有向跳距**分层而不是按类型。
4. **配色取自 AWS Cloudscape 图表令牌**（7 组分类色）：
   `#3759ce` 应用与计算 · `#2ea597` 数据存储 · `#688ae8` 入口与路由 ·
   `#8456ce` Agent/GenAI · `#b2911c` 消息 · `#e07941` 业务能力 · `#8c8c94` 基础设施。
   锚点用 AWS 品牌橙 `#ff9900` + Squid Ink `#232f3e` 描边。
5. **形状做冗余编码**（色盲可用）：dot / square / triangle / triangleDown /
   diamond / hexagon，star 保留给锚点。
6. **超预算告警**。节点数超过 50 会直接在页面上说「已超过可读上限」并给出收敛建议；
   裁剪按「离锚点近」BFS，不做任意截断。

### 3.3 交互方式

- **滚轮**缩放
- **按住空白处拖动**平移（横向纵向都可以）
- 右下角**导航按钮**
- **悬停节点**看类型 / 名称 / 分组；**悬停边**看关系类型与验证状态

画布固定在视口内（560–900px），图靠 `fit` + 平移浏览，缩放设了 **0.75 的可读下限**——
装不下就保持可读比例并对准锚点，剩下的拖着看。

### 3.4 边的颜色 = 验证状态（不是关系类型）

29 种关系类型远超颜色上限，所以**关系类型放在边标签上**，颜色让给更重要的信息：

| 样式 | 含义 |
|---|---|
| 🟢 绿粗线 `#67a353` | 故障注入**已确认** |
| 🔴 红虚线 `#ba2e0f` | 已**证伪**，不成立 |
| 🟠 橙线 `#cc5f21` | 未定 |
| ⚫ 灰细线 `#b4b4bb` | 未验证 |

「这条依赖到底成立吗」才是本平台的核心信息，值得占用颜色这个最强通道。

### 3.5 第 9 页（Interactive Explorer）与第 3 页的分工

| | 第 3 页 Graph Explorer | 第 9 页 Interactive Explorer |
|---|---|---|
| 引擎 | pyvis / vis-network | Cytoscape（`st-link-analysis`） |
| 定位 | **静态分层总览**：一个场景一张图 | **交互探索**：从一个点自己走出去 |
| 交互 | 缩放 / 平移 / 悬停 | 展开邻居、选中回传 Python、面包屑回退 |
| 布局 | hierarchical（UD） | dagre |

第 9 页能做第 3 页做不到的事：**选中的节点能回传到 Python**，
所以「点节点 → 出侧栏详情 → 再展开」这套成熟模式只能在它上面实现
（pyvis 是单向的，这是硬天花板）。侧栏会给出该节点的类型、分组、度数，
以及**被依赖 / 依赖两个方向**的关系表（含验证状态）和可下钻的查询指引。

## 5. 一个必须知道的事实：验证判定会随时间变化

同一天实测四次，`confirmed` 占比从 **16.82% → 13.08% → 12.15% → 11.21%**，
`refuted` 从 3 条归零。原因是 2026-09-05 引入了「独立证据门禁」——
**有独立观测源看到过的边，永不得判 refuted**。

所以：演示时看到的数字和本文档记录的不会完全一致，**这是正常的**。
界面刻意不假设 `refuted > 0`。

## 6. MCP Server：同样的 24 条查询，给 Agent 用

24 条查询已包成 MCP server 部署在 **AgentCore Runtime**，
并关联进 **AWS DevOps Agent**（24 个工具全部 `READ_ONLY`）。

| 资源 | 标识 |
|---|---|
| AgentCore Runtime | `graph_dependency_mcp-12Vg2Z9XXu`（v2，READY） |
| DevOps Agent space | `petsite-devops` |
| 认证 | SigV4 与 Cognito M2M OAuth 双路径均实测通过 |

意味着同一套确定性查询有两个消费者：**人**（第 2 页界面）和 **Agent**（MCP 工具），
共用同一个 `graph_contract_version`，不存在两套真相。

### 6.1 端到端实测（2026-09-05 08:10）：从 71% 修到 96%

只验「协议通不通」是不够的。用每个工具 schema 里的必填参数填真值逐一试跑，
测出**真实可用率**：

| 轮次 | 正常 | 缺模块 | 其他 | 可用率 |
|---|---|---|---|---|
| 修复前 | 17 | **6** | 1 | 71% |
| 修复后 | 23 | 0 | 1 | **96%** |
| 修正测试数据类型后 | **24** | 0 | 0 | **100%** |

**缺模块（真 bug）**：`mcp/build_package.sh` 拷了 `dr-plan-generator/graph/`
但漏了 `dr-plan-generator/config.py`，而 `graph/neptune_client.py` 顶层
`import config`。受影响的正好是 6 条 `mod=dr` 查询
（q12_az / q12_service / q13 / q14 / q15 / q16），占 24 个工具的 **25%**。

这个 bug 之前查不出来，因为它**只在带上有效参数调用时才暴露**——
无参调用先被参数校验挡住，返回「缺少必填参数」这个看起来正常的响应。
无参冒烟测试对它完全免疫。

**「其他」那一条不是 bug**：`q11_broader_impact` 要的是 `ec2_ids`
（字符串列表），测试脚本塞了个字符串，Neptune 回 400。
换成真实 EC2 id 后返回 38 行（那台实例故障会波及的服务/Pod）。

### 6.2 一个会误导排查的坑：固定 Mcp-Session-Id

修复部署成 v3、`liveVersion: 3`、`status: READY`、S3 产物指向也对，
但探测脚本仍然报同样的 `ModuleNotFoundError`。

原因是脚本一直复用同一个 `Mcp-Session-Id`，请求被**粘在 v2 的热容器**上。
换成每次调用生成新 UUID，立刻拿到修复后的结果。

> 排查 AgentCore 上的 MCP server 时，验证新版本**必须**用新 session id，
> 否则会得出「部署没生效」的错误结论。

### 6.3 实测的排查链（证明工具串起来有用）

情景「petsite 变慢」，一个运维 Agent 的实际走法：

| 步 | 工具 | 结果 |
|---|---|---|
| 1 | `q12_service_dependency_tree(service_name=petsite)` | 22 行依赖树 |
| 2 | `q22_edge_verification_verdicts(limit=100)` | confirmed 13 / inconclusive 25 / untested 62；降级最狠 `petsearch → dynamodb` **降 100%**、信度 0.9998 |
| 3 | `q16_single_point_of_failure()` | 5 个单点，首个是 `i-078e14ddd7e0cac06`（EC2，单 AZ `ap-northeast-1a`） |
| 4 | `q15_critical_path()` | 21 行关键路径 |
| 5 | `q23_verification_coverage()` | 覆盖率汇总 |

**参数命名要注意**：`q3_upstream_deps` 用 `failed_service`、
`q1_blast_radius` 用 `failed_node`、`q12_service_dependency_tree` 用 `service_name`
——不统一。好在参数校验的报错会**列出该查询接受的全部参数名**，
Agent 一次重试就能自纠。

## 7. 已知限制

- **横向超宽时需要拖动**。1 跳邻域常有十几个兄弟节点，在 0.75 缩放下限下会超出画布宽度，
  需要横向拖动查看。这是刻意取舍：保住标签可读优先于「一屏装下」。
- **节点名超过 18 字符会截断**（悬停可看全名）。为的是避免同层标签互相糊住。
- **消息与数据存储共用 square 形状**（颜色差异极大）。vis-network 里按 `size` 缩放的形状
  只有 7 种，star 又要留给锚点。
- **第 9 页依赖 `st-link-analysis`**，缺失时页面会给出降级提示而不是崩溃。

## 8. 排障

| 现象 | 原因与处置 |
|---|---|
| 页面显示「契约文件读不到」 | 部署遗漏 `profiles/graph_contract.yaml`。该文件是唯一真相源，缺失时界面**显式报错而不显示 0**——显示「0 种节点类型」比报错更糟，那是在撒谎。 |
| 侧栏显示「离线快照模式」 | Neptune 不可达。检查安全组与 `NEPTUNE_ENDPOINT`。功能仍可用，数据是真实快照。 |
| 第 9 页提示缺依赖 | 部署主机需 `pip install --user --break-system-packages st-link-analysis`（Ubuntu 系统 Python 有 PEP 668 限制）。 |
| 图谱空白 | 看该页的关系类型勾选——若把 6 种依赖边全取消了就会是空图。 |
