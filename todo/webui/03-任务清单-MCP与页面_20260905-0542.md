## 为什么要带 provenance（核心设计约束）

2026-09-01 的 SAP 盲发现验证里，DevOps Agent 独立从 CloudTrail 找到了 FIS 实验，
但**编造了 CWAgent 指标值、用虚构的 iowait 排除存储瓶颈**。所以本 MCP server 的
每个响应必须带出处，且必须在 MCP `initialize` 的 `instructions` 里写明证据纪律：
`untested` 必须声明、`refuted` 不得用于推理。否则 agent 会把图谱事实与自己的
推断混为一谈，换个地方犯同一个错。

## 重要实测发现（写下来免得下轮重查）

**验证判定会随时间变化。** 05:00 抓快照时是 confirmed 15 / refuted 3 /
inconclusive 19 / 覆盖率 16.82%；05:50 变成 confirmed 14 / refuted 0 /
inconclusive 23 / 覆盖率 13.08%。原因不是数据错乱——边上的 `verify_reason`
明确写着：**2026-09-05 引入了「独立证据门禁」**，只要该边被任何独立观测源
看到过（DeepFlow calls 计数非零），就永不得判 refuted，于是那 3 条被主动
撤销成 inconclusive。

后果：
1. UI 不能假设 refuted > 0（已确认代码是从数据现算的，0 条时不显示该段）
2. fixtures 需要刷新
3. MCP server 的 instructions 里已写明这道门禁，免得 agent 把 refuted=0
   读成「没做验证」

**22 条查询的返回形状有三类**（实测）：12 条行列表、3 条单 dict
（q1/q4/q10，加新增的 q23）、1 条字符串（q8）、5 条当前为空。
响应里已加 `result_shape` 字段告诉 agent 拿到的是哪种。
