## 0. 两个必须先纠正的判断错误

**错误一：我把它叫「毛线球」，判断错了。**
88 节点 / 146 边 = 平均度 **3.3**、密度 **0.038**（3828 种可能的边里只有 146 条）。
这是**稀疏图**。它难看不是因为边多，而是因为力导向布局把数据里最强的两个信号扔了：
**方向**与**天然分层**。

**错误二：邻接矩阵在这里帮不上忙。**
「矩阵优于节点链接」的经典结论（Ghoniem/Fekete/Castagliola, InfoVis 2004，阈值约 20 节点）
针对的是**密集**图。Okoe/Jianu/Kobourov 2017（TVCG 2018）在 **258 节点、密度 0.016**
的稀疏图上用 **557 名被试**做对照，结论相反：**稀疏图上节点链接反而胜过矩阵**，
理由是「空矩阵和满矩阵占一样大的地方」。所以矩阵这条路对本项目的数据是错的。

## 1. 认知预算（有硬数字）

**Yoghourdjian 等，*Scalability of Network Visualisation from a Cognitive Load
Perspective*，IEEE TVCG 2020**（EEG + 眼动对照实验，arXiv:2008.07944）：

- 节点超过约 **50 个**（密度 6）或约 **100 个**（低密度 2）时，被试**答错或不确定的
  比例超过 50%**
- 密度 6 且 ≥75 节点时，准确率降到**随机水平**
- 论文明确建议：在 overview+detail 的节点链接视图里**给邻域大小设上限**
- 另引 Ware 等的发现：**路径上的跳数是认知成本的最大单一来源**

→ 首屏目标 **20–30 个可见节点**，默认 **1 跳**。

**感知通道上限**（arXiv:2103.06084）：**颜色可区分上限约 7 类、形状约 5 类**。
本项目有 **39 种节点类型、29 种边类型**——**没有任何首屏能同时用颜色编码它们**。

## 2. 10 个成熟产品的共同做法

调研了 Datadog Service Map / New Relic / Dynatrace Smartscape / ServiceNow CSDM /
Backstage / Cartography / Neo4j Bloom & Browser / AWS graph-explorer /
Grafana Node Graph / Kiali。**共同模式如下，而全图力导向渲染违反了几乎每一条：**

| # | 模式 | 证据 |
|---|---|---|
| 1 | **从不渲染全图** | Bloom 与 graph-explorer 开局是**空画布 + 搜索种子**；Bloom 的「Show me a graph」返回的是**采样**；Kiali 强制先选 namespace；Grafana **默认只画 200 个节点**、其余折成可点的「隐藏节点」标记；Datadog 限定单一 `env` |
| 2 | **锚点 + 有界邻域，按需展开** | Backstage 的 `maxDepth` 是 API 参数；graph-explorer 双击展开一阶邻居且**可限制结果数**；ServiceNow 节点带 `+/-` 展开器 |
| 3 | **方向编码进布局** | Datadog：「左边的服务靠近客户，右边的更可能是根因」；Dynatrace Smartscape 垂直分层 |
| 4 | **默认布局是分层的，力导向只是大图兜底** | Grafana 默认 **Layered**（「对服务图特别有用」），并明确写 **force 只建议 500+ 节点** |
| 5 | **靠聚合驯服枢纽节点** | Kiali 四级聚合（workload/app/versioned-app/service）+ namespace 盒子；Datadog 按调用量自动聚类 |
| 6 | **状态画在图上** | 边颜色 = 流量健康度、边粗细 = 请求量、节点环 = 错误率（Grafana `arc__*`）；Datadog「越红错误率越高」 |
| 7 | **Find/Hide 是一等公民，用来压掉已知噪声** | Kiali 文档教你用 `node = unknown` 隐藏探针/抓取噪声，且**默认关掉 idle 边**「以呈现更干净的图」 |
| 8 | **选中 → 侧栏详情**；单击 ≠ 双击 | 近乎通用约定 |
| 9 | 一切按时间 + 环境 + 类型限定 | Datadog：换 scope「会画出完全不同的图」 |
| 10 | 类型用形状 + 图标 + 颜色，配图例 | Kiali 节点形状 = 组件类型 |

**一句话**：锚点 + 邻域 + 渐进展开 + 分层布局 + 聚合 + 状态上边 + 侧栏详情。

## 3. 最省力且价值最高的一招：数据里已经有了

契约的 `dependency: true` 标记把 29 种边分成两类：

- **6 种依赖边**：`Calls` / `AccessesData` / `DependsOn` / `Delegates` /
  `InvokesTool` / `Retrieves` —— 「A 依赖 B」的语义断言，**该画成箭头**
- **23 种结构边**：`RunsOn` / `LocatedIn` / `BelongsTo` / `Contains` / `Routes` /
  `Manages` … —— 包含/承载关系，把它们也画成箭头**正是杂乱的主要来源**

调研把这条列为「最高价值、近乎零成本」，通常一下砍掉一半可见边。
改造前的实现是 29 种边一视同仁全画。

被明确判为**不适用**的两项：
- **边捆绑（edge bundling）**：牺牲边的可追踪性换取视觉平滑，而依赖图恰恰需要
  「A 到底调了谁」；146 条边也远未到需要捆绑的密度
- **骨架提取（disparity filter，Serrano PNAS 2009）**：需要**边权重**做统计显著性
  检验，本项目的边是分类型的、无权重，无从过滤

## 5. 布局算法

| 方案 | 环处理 | 质量 | 成本 |
|---|---|---|---|
| **vis-network `hierarchical`** | ❌ 无 feedback-arc-set，遇环层级会算乱（需显式钉 `level` 绕开） | 交叉较多，无正交布线 | **1 小时**（零新依赖） |
| **dagre** | ✅ 贪心 FAS | 好（network-simplex + Brandes–Köpf） | 半天 |
| **ELK / elkjs** | ✅ 可配 4 种策略 | **最好**，正交布线 + 嵌套复合节点 | 1–2 天 |
| **Graphviz `dot`** | ✅ DFS 反转 | 优秀，`rank=same` 可钉类型层 | 半天（但产物是静态 SVG，无交互） |

Graphviz 引擎选择：`dot` 是唯一合适的（`neato`/`fdp`/`sfdp` 都是无向力导向、
仍是散点；`sfdp` 面向数千至百万节点，此处过剩；`patchwork` 是 treemap、不画边）。

**A 档实测发现（第二轮踩的坑，别重犯）：**

1. **场景也必须有锚点。** 第一版给 4 个场景配了边类型预设但没配锚点，
   于是「依赖验证现状」是**全图查询** → 107 条边 / 66 个节点，
   分层布局把它们压成一条细带，比散点更不可读。「锚点 + 有界邻域」
   是调研里排第一的建议，不是可选项。
2. **Neptune 不吃变长路径 + 谓词。** 写
   `MATCH p = (a)-[r*1..N]-(b) WHERE ALL(x IN r WHERE type(x) IN [...])`
   `UNWIND relationships(p)` 直接回 **400 Bad Request**。
   改成 **Python 侧迭代单跳扩展**（纯基础语法，一定能跑，跳数边界还更可控）。
3. **画布高度必须自适应。** 固定 640px + 同层十几个节点 = `nodeSpacing`
   放不开，被压成细带。按最宽那一层算高度（`widest * 46 + 120`，上限 1600）。
4. **锚点视图要按有向跳距分层，不是按类型。** 上游调用者往往和锚点同类型
   （都是 Microservice），按 `TYPE_LEVEL` 分会把它们和锚点堆在同一列。
   改为「相对锚点的有向跳距」：调用方在左（负）、锚点居中（0）、依赖在右（正），
   即 Datadog 的「左边靠近客户、右边更可能是根因」。
5. **超预算要按「离锚点近」裁剪**，不能任意截断——任意截断会砍掉锚点的直接邻居
   而留下无关的远端节点，比不裁更糟。

**A 档实测结果**（锚点 petsite，1 跳，6 种依赖边）：
17 条关系 / 18 个节点 / 在预算内 / **0 异常** / 实时模式；
左列上游（trafficgenerator、gateway-service、order-service）→ ★ petsite →
右列下游（数据库绿柱、ssm/sts 灰菱、微服务蓝点、SQS 黄方）。
线上部署于 2026-09-05 14:59:54（pid 54936），日志无异常。
