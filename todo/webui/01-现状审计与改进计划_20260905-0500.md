### S2 — 项目最强的能力零曝光

`profiles/graph_contract.yaml:825` 的 `edge_verification` 块是完整的证伪模型，界面完全没有：

- 6 个边属性：`verify_status`、`verify_confidence`、`verify_last`、`verify_by`、`verify_experiment`、`verify_degradation`
- 4 种状态：`untested` / `confirmed` / `refuted` / `inconclusive`
- 证据权重：干预确认 **±4.0**（不设上限）vs 静态声明 +1.0 vs 每个观测源 +0.5（**上限 1.5**）——「主动干预一次，比被动观测多少次都值钱」这个立场是可直接展示的产品主张
- 阈值：确认 ≥20% 退化、证伪 ≤5% 退化且**必须有注入生效证据**、观测流量下限 20 请求、验证 30 天过期

同样零曝光的还有：agent 域 6 类节点、契约 12 个合法 source 的写入门禁、节点/边过期收敛、59 条故障目录。

## 4. 改造方案

### 4.1 主张换轨（首页重写）

原首页结构是「标题 → 5 个指标 → 功能表 → 技术栈 → ASCII 架构图 → Schema 两个 tab」，是产品目录。

新结构按 `todo/project-intro-outline_20260831-0750.md` 的叙事骨架（该文档 1834 行，专为对外讲解写的）：

1. **主张**：「市面上的依赖图都在回答『我看到了什么』。这个项目回答的是『我看到的是真的吗』。」
2. **两个观众答不上来的问题**：你怎么知道图上那条边是真的？如果图上少了一条边，你有任何机制会发现吗？
3. **验证计分板**（实时）：107 条依赖边 · 15 确认 · 3 证伪 · 19 未定 · 70 未测 · 覆盖率 16.82%
4. **四种业界范式对照**：ServiceNow IRE（属性级仲裁）/ Backstage（声明式单一权威）/ Cartography（全量扫描时间戳收敛）/ New Relic·Dynatrace（实体 + TTL）——并点出 Datadog / OTel service graph / Elastic APM **根本没有持久化边实体**，所以「这条边消失了吗」在那里无法回答
5. **缺口**：四种范式都在裁决「哪个源对」，没有一个验证「这些源合起来对不对」
6. **证据卡**（每条带出处标签）：单一观测源导致 **85% 假阴性**、唯一没门禁的字段上 **43% 漂移**、一次不带标签的查询造成 **183 条边源端点错误**、count 正确但 join 放大 **40 倍**、`abort` 故障下成功率**是盲的**
7. 动态数字全部从 `graph_contract.yaml` 现算，不再硬编码

### 4.2 新增页面

| 页面 | 内容 | 依赖 |
|---|---|---|
| **6_Edge_Verification**（核心） | 覆盖率计分板、按状态/类型下钻的边表、`verify_confidence` 与退化幅度、评分规则（权重从契约读）、「注入 B 观测 A」原理图、被证伪的 3 条边单独展示 | Neptune 只读 |
| **7_Agent_Dependencies** | 6 类 agent 节点 + 5 类 agent 边；孤岛问题与唯一桥接路径 `AgentTool -[DependsOn]-> Microservice`；Strands 实时元数据（token / cycles / tool trace） | Neptune 只读（+Bedrock 可选） |
| **8_Query_Catalog** | 22 条查询浏览器：选查询 → 填参数 → 看生成的 Cypher → 执行 → 结果表。**不需要 Bedrock**，是给访客最安全的互动入口 | Neptune 只读 |

### 4.3 互动性改造（对应「愿意试、多互动」）

- **离线 fixture 包**：从活图谱抓真实数据存 `demo/fixtures/*.json`。无凭证访客点任何页面都能看到**真数据快照**而不是报错，也不是编的数据。页面顶部明确标注「离线快照 / 实时」两种状态。
- **每页一个「先试这个」入口**：预置一个必然有结果的操作，访客不用想参数。
- Graph Explorer 图例补全 22→39 项、节点类型从契约动态生成。
- Smart Query 增加离线预置问答对，无 Bedrock 也能看到 NL→Cypher 的效果。
- RCA 去掉假进度条，改为展示真实执行的步骤；补离线示例报告。

### 4.4 安全与正确性

- 删除页脚 Account ID
- 混沌页 `💥 执行实验` 改为**默认禁用**，需环境变量 `DEMO_ALLOW_INJECTION=1` 才出现；线上不设该变量
- 混沌目录从 `fault_catalog.yaml` 动态读（59 条），不再硬编码 73 条
- DR 示例指标从 JSON 现算，不硬编码
- 新增 `demo/_common.py`：统一 path/env、契约加载、Neptune 连接与降级、fixture 加载、侧栏；消掉 5 份重复样板
- 对 Strands 引擎 / DR registry / GraphAnalyzer 加 `@st.cache_resource`

### 关键事实

**Neptune 与 EKS PetSite 在同一个 VPC**，且 Neptune 的子网是 EKS 子网的子集：

| 资源 | VPC | 子网 |
|---|---|---|
| Neptune `petsite-neptune` | `vpc-010ab37a3f9f74725` | `subnet-0f801fa79077eb277`、`subnet-047a94f9c5ab6302a` |
| EKS `PetSite`（1.35） | `vpc-010ab37a3f9f74725` | 上述两个 + `subnet-02ebd1dd8d1681da8`、`subnet-0600a43fa7ebf1ffe` |
| 当前 demo 主机 | `vpc-06731f30388b57818` | 跨 VPC peering |

### 推荐：迁到 EKS PetSite 集群（Deployment + Service + TargetGroupBinding）

理由，按权重排序：

1. **与 Neptune 同 VPC**，去掉 peering 这一跳；现在的跨 VPC 路径是额外故障面
2. **凭证走 IRSA**，机器上不再需要长期凭证；Neptune 只读 + Bedrock 调用都按服务账号最小授权
3. **本仓已验证过该模式**：`todo/loadtest/petsite-loadtest-tgb.yaml` 就是用 TargetGroupBinding 把 EKS Pod 挂进现有 ALB 目标组
4. **变成 IaC**，摆脱「一台机器上的手工 systemd + 手工 ALB 规则」
5. **ALB 规则与 Cognito 完全不动**——只是把 `streamlit-demo-tg` 的目标从固定 IP 换成 TGB 管理的 Pod IP，回滚就是删掉 TGB 重新注册 IP
6. `openclaw-instance-v2` 是 OpenClaw 主机，用户已明确后续不在其上做 AI 编程工作，把演示界面绑在一台待退役的机器上是风险

**必须注意的约束**：该集群 CPU 已紧张（观测栈 request 2054m 比被观测应用的 1892m 还多，曾出现无节点放得下 544m）。所以 Deployment 的 CPU request 要压到 100–200m，先 1 副本，别按默认值申请。

**其他选项评估**

| 选项 | 判断 |
|---|---|
| 保持现状（openclaw + systemd） | 能用，但绑在待退役主机 + 跨 VPC + 无 IaC，三项都是负债 |
| ECS Fargate（同 VPC） | 可行，无集群 CPU 压力，但要新建一套基础设施，收益不如复用 EKS |
| App Runner | 需要 VPC connector 才能访问 Neptune，成本更高且无额外收益，不推荐 |
| 独立小 EC2（PetSite VPC 内） | 比现状好（同 VPC），但仍是手工机器，只是把问题搬了个地方 |

**迁移不阻塞本次改造**：代码改动与落位解耦。先在现有主机上更新代码验证效果，迁移作为独立一步。
