### 三项负债

1. **跨 VPC**：主机在 `vpc-06731f30388b57818`，Neptune 在 `vpc-010ab37a3f9f74725`，靠 peering 打通——多一跳、多一个故障面。
2. **主机待退役**：这台是 OpenClaw 主机，用户已明确后续不在其上做 AI 编程工作。把对外演示界面绑在一台待退役机器上是风险。
3. **无 IaC**：systemd 单元手工建、ALB 规则手工加，重建全靠人记得。

## 2. 关键事实：Neptune 与 EKS 同 VPC

| 资源 | VPC | 子网 |
|---|---|---|
| Neptune `petsite-neptune` | `vpc-010ab37a3f9f74725` | `subnet-0f801fa79077eb277`、`subnet-047a94f9c5ab6302a` |
| EKS `PetSite`（v1.35） | `vpc-010ab37a3f9f74725` | 上述两个 **+** `subnet-02ebd1dd8d1681da8`、`subnet-0600a43fa7ebf1ffe` |
| 目标组 `streamlit-demo-tg` | `vpc-010ab37a3f9f74725` | —（`targetType=ip`） |
| 当前 demo 主机 | `vpc-06731f30388b57818` | 跨 VPC |

**Neptune 的子网组就是 EKS 子网的子集。** 把界面放进 EKS，它与 Neptune 就在同一网段内。

## 3. 推荐方案：EKS Deployment + TargetGroupBinding

按收益排序：

1. **与 Neptune 同 VPC** —— 去掉 peering 一跳
2. **凭证换 IRSA** —— 机器上不再需要长期凭证；Neptune 只读与 Bedrock 调用各自最小授权
3. **本仓已验证过该模式** —— `todo/loadtest/petsite-loadtest-tgb.yaml` 就是用 TargetGroupBinding 把 EKS Pod 挂进现有 ALB 目标组
4. **变成 IaC** —— 清单在 `infra/k8s/streamlit-demo.yaml`
5. **ALB 与 Cognito 完全不动** —— 只换目标组的后端；回滚就是删 TGB、把 IP 目标注册回去
6. **摆脱待退役主机**

### 必须注意的约束

| 约束 | 处理 |
|---|---|
| 集群 CPU 紧张（观测栈 request 2054m > 被观测应用 1892m，曾无节点放得下 544m） | 清单里 CPU request 压到 **200m**、**1 副本**。不要照抄默认值 |
| 节点是 Graviton（arm64） | 镜像必须 `--platform linux/arm64`；清单加了 `nodeSelector: kubernetes.io/arch: arm64` |
| 固定 tag 不触发滚动更新 | 用 git sha / 日期 tag。本仓踩过：镜像内容变而 `:latest` 不变时 Deployment spec 无变化，`imagePullPolicy: Always` 只在创建容器时生效，救不了 |
| Streamlit 冷启动较慢 | `startupProbe` 给 150s 宽限（本仓踩过 search-service 探针宽限期短于真实启动时间导致循环重启） |

### 其他选项

| 选项 | 判断 |
|---|---|
| 保持现状 | 能用，但跨 VPC + 待退役主机 + 无 IaC 三项负债都在 |
| ECS Fargate（同 VPC） | 可行，无集群 CPU 压力，但要新建一套基础设施，收益不如复用 EKS |
| App Runner | 需 VPC connector 才能访问 Neptune，成本更高且无额外收益，**不推荐** |
| PetSite VPC 内另起小 EC2 | 比现状好（同 VPC），但仍是手工机器，只是把问题搬了个地方 |

## 4. 执行步骤

### 第一步：先更新现有主机（立即见效，低风险）

代码改动与落位解耦，可以先让线上用上新界面：

```bash
# 在 i-022fb7c32b71c72d9 上
cd /home/ubuntu/tech/graph-dependency-platform
git pull
pip install -r demo/requirements.txt        # 本次新增 pyyaml、pydantic
sudo systemctl restart streamlit-demo.service
systemctl is-active streamlit-demo.service
curl -sI https://rainmeadows.com/streamlit/_stcore/health
```

> ⚠️ `pyyaml` 与 `pydantic` 是新依赖。`pyyaml` 缺失会让所有页面失去动态计数，
> `pydantic` 缺失只会让 Smart Query 的 few-shot 面板降级（已加保护，不会整页崩）。

### 第二步：迁到 EKS（独立进行）

1. 建 ECR 仓库并构建 arm64 镜像（`demo/Dockerfile`，构建上下文是**仓库根目录**）
2. 建 IRSA 角色，subject `system:serviceaccount:petadoptions:streamlit-demo-sa`，
   权限 `neptune-db:ReadDataViaQuery` + `bedrock:InvokeModel*`
3. 把角色 ARN 与镜像 tag 填进 `infra/k8s/streamlit-demo.yaml` 的两处 `REPLACE-`
4. `kubectl apply -f infra/k8s/streamlit-demo.yaml`
5. 等 Pod ready，确认目标组里出现 Pod IP 且 healthy
6. **两个目标共存期**：Pod IP 与 10.1.2.198 会同时在目标组里，流量各分一半——
   用于对比验证。确认无差异后再去注销 IP 目标
7. 注销 `10.1.2.198:8501`，停用旧主机的 systemd 服务
8. 回滚路径：`kubectl delete -f infra/k8s/streamlit-demo.yaml` + 重新注册 IP 目标

### 验收

- [ ] `https://rainmeadows.com/streamlit/` 经 Cognito 后正常打开
- [ ] 目标组健康检查 `/streamlit/_stcore/health` 通过
- [ ] 首页各数字非零（说明 Pod 真的连上了 Neptune，而不是回落到离线快照）
- [ ] 混沌页**不出现**真实注入按钮（确认未设 `DEMO_ALLOW_INJECTION`）
- [ ] Pod 无重启（`kubectl get pod -n petadoptions -l app=streamlit-demo`）
