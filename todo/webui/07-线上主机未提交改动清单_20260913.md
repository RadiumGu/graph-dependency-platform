## 为什么记这一份

`demo/README.md` 写的更新流程是 `git pull` + 重启，但主机的实际状态不是这样：
它停在 `main` 的一个旧提交上，靠 **40 项未提交改动**承载线上真正在跑的代码 ——
旧页面以删除（`D`）存在，新页面以未跟踪文件（`??`）存在。

后果是**线上状态没有可靠的 git 记录**：无法用一个 commit 复现线上、无法可靠回滚，
下一个人（包括未来的自己）会重新困惑一遍。这不是本次改动引入的，但现在也盖住了
本次改动。

本次发布因此没有走 `git pull`，而是 `git checkout origin/<分支> -- <指定文件>`
只取需要的路径，不切分支、不动其余未提交改动。覆盖前对比过 md5，确认线上文件与
提交前版本一致，没有未知的手工热修。

## 建议怎么处理

按风险从低到高：

1. **先确认作者与意图。** 这些改动不是本次会话产生的，每一项的意图未知。
   直接提交等于替原作者做决定，而且如果有人正靠这个状态调试，会被打断。
2. **把线上跑的那份落成一个提交。** 至少让「线上 = 某个 commit」成立，
   之后回滚才有对象。
3. **让部署可复现。** 根因是部署方式本身：手工放文件的流程无法审计。
   `infra/k8s/streamlit-demo.yaml` 已经有容器化落位方案，
   走那条路可以一并解决版本可追溯的问题。

在 1 完成之前不要执行 2 —— 提交一批意图不明的改动，比留着它们更难回退。
