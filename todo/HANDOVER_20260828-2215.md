## 2. 最有价值的发现

按影响排序,全部有实测证据:

**① 图谱在断言不存在的依赖**(cycle 1–6)
18 条 `Calls` 边中 **17 条陈旧 2–5 个月却全部 `active=true`**;
其中 `gateway-service` 所属命名空间 6 个 Deployment 已全为 0 副本。
`active`/`last_seen` 字段早就写入,但**全仓无任何消费方** ——
这是本次工作反复出现的模式的第一例。

**② 向量索引 56% 是孤儿**(cycle 18)
18 条向量里 10 条对应的 Incident 在图谱中**根本不存在**。
而 `search_similar` 的输出会作为「语义相似历史案例」注入 RCA 提示词 ——
等于给 RCA 喂**无法核实的先例**。根因是写入有 `index_incident`
而清理**没有对应函数**,测试只删节点不删向量,一天内索引从 18 涨到 56。

**③ profile 的 `${}` 占位符从来没被展开**(cycle 17)
`profile_loader` 完全没有展开逻辑,5 个占位符对任何消费方都是字面字符串。
chaos 因此拿到 `https://${NEPTUNE_ENDPOINT}:8182`,写图谱全部 DNS 失败。
profile 自称单一配置源,对这些键却只是装饰。

**④ 测试套件在本机根本跑不起来**(cycle 15–19)
`conftest.py` 硬编码 `/home/ubuntu/tech/...`,导入即失败 ——
所谓「277 个测试」在原开发机之外**一个都没运行过**(实际是 466 个)。
修通后查清 7 个根因,**只有 2 个是「测试写错了」**,其余 5 个是真缺陷:
profile 占位符、conftest 把 Lambda 部署包放进全局 `sys.path`(整个 session
用 vendored 副本)、两个同名包互相遮蔽、`base.py` 的 f-string 在 3.12 前无法解析、
向量孤儿。**它们全部被「套件跑不起来」掩盖。**

**⑤ 一份编造先例的 Bedrock KB**(早期)
在 1 篇文档的语料上,检索得分与相关性**反相关**(乱码 0.8916 > 真相关 0.7706),
向每次 RCA 提示词注入「相似度 89%」的虚假先例。已删除。

**⑥ 自动化闸门的乐观偏置**(cycle 19–20)
`confidence = max(规则分, LLM 分)`,而规则分在 **40% 的生产 Incident 中饱和到 1.0**
(126 个中 50 个,还有一个 **1.1** —— 越界说明某条路径完全绕过上界)。
饱和后 LLM 的判断被完全覆盖:即使模型说「置信度 35,证据很弱」仍走到 `auto`。

## 3. 反复出现的三个缺陷模式

**模式 A:写了没人读。** `active`/`last_seen`、`causal_weight`、
韧性分数(读取方查的四个属性名活图里 0 个节点拥有)、`generate_group_report`
(调用了一个不存在的函数,靠 fallback 掩盖)。
本次新增机制时都强制配了消费方,并写进测试断言。

**模式 B:静默失败。** 13+ 缺陷中约 11 个是异常被吞或日志级别过低。
最典型的是 `from config import FEATURE_FLAGS` 包在 `except Exception: pass` 里 ——
`auto_remediation_enabled` 这个用来阻止自动修复的开关**从未被检查过**。

**模式 C:两份实现互相掩盖共有缺陷。** 四份 Neptune 客户端**全部**每次调用
新建 `boto3.Session`(9.7ms)。我一开始把两个客户端互比,只看到 6.7ms 之差,
据此判断「不值得动」—— 直到单独测 `Session()` 的绝对成本才发现共同开销。
**比较两个实现时,它们共有的缺陷是不可见的。**

### 硬删除:建议**不启用**(`CALLS_EDGE_DROP_ENABLED` 保持 false)

观测数据(4.6 小时,ETL 调用 73 次):

```
18 条 Calls 边:1 active / 17 inactive，自 17:36 起稳定
活跃边 petsite→petsearch   last_seen 0 分钟前（每轮持续刷新）
最"新"的失效边             59.6 天前 —— 相对 1800s 阈值有 2860 倍余量
零误判、零翻转
```

**除了「软删除已达成目标」之外,T-030 之后出现了一条新的反对理由**:
拓扑变更日志记录的是「这条依赖**何时**停止被观测」,而失效边本身承载
「它**曾经存在**」。硬删除会删掉后半句 —— 变更事件将指向一条不存在的边,
「依赖消失」这个结论就失去了可核实的对象。

即:**T-030 让保留失效边从「无害」变成了「有用」。**

### 明确决定不做的

**T-031 基线快照 + 事件重放**(答「T 时刻完整拓扑」)。
不做的理由:现有变更日志已答「T 附近变了什么」,而后者才是 RCA 实际问的;
「完整拓扑」目前**没有任何已知消费方在要**。且快照会引入第二个存储 ——
向量索引 56% 孤儿就是活生生的反例,一个与图谱漂移的旁路存储比没有它更糟。
要做必须同时设计一致性校验(类似 `test_26`)。
